# PRIME Mission Planner · ЛЦТ 2026 · Геоскан

**Трек №5 — «Сервис планирования и распределения беспилотных авиационных работ».**

Веб-стенд помогает составить задание для группы БВС, распределить работы и батареи, сравнить варианты расписания, проверить ограничения и показать выполнение на 2D-карте. Результат — план группы и отдельных аппаратов, исходное задание для повторного расчёта и пакет проверяемых доказательств.

Версия расчётного ядра: **0.3.0**. Формат миссии: **2.0**. Это инженерный MVP для экспертной оценки: **не автопилот, не реальная телеметрия и не разрешение на полёт**. Полное выполнение ТЗ и официальный балл не заявляются.

## Получить исходники

Репозиторий **закрытый**: [MasterKSAF/prime-geoscan-lct2026](https://github.com/MasterKSAF/prime-geoscan-lct2026). Для клонирования нужен GitHub-аккаунт с предоставленным доступом и настроенная авторизация Git. Не вставляйте токены в URL или команды.

```powershell
git clone https://github.com/MasterKSAF/prime-geoscan-lct2026.git
cd prime-geoscan-lct2026
```

## Быстрый запуск: Docker

Нужны Docker Engine / Docker Desktop с Linux-контейнерами и Compose v2. GPU, ключи API и аккаунт облачного сервиса не требуются. Для первой сборки нужен интернет: загрузка базового образа и npm-зависимостей.

Из корня клонированного репозитория:

```powershell
docker compose -p lct -f compose.planner.yaml up --build -d
docker compose -p lct -f compose.planner.yaml ps
```

Откройте **[http://127.0.0.1:3016/planner](http://127.0.0.1:3016/planner)**. Первая сборка включает проверку типов, модульные тесты и сборку интерфейса; дождитесь состояния `healthy`.

Проверка API в PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:3016/api/planner/health
```

Ожидаются `missionEngineVersion: "0.3.0"`, `missionSchemaVersion: "2.0"`, `flightReady: false`. Поле `engineVersion` относится к старому диагностическому ядру и не определяет версию миссий.

```powershell
# Посмотреть последние сообщения
docker compose -p lct -f compose.planner.yaml logs --tail 100 planner

# Остановить, не удаляя контейнер
docker compose -p lct -f compose.planner.yaml stop

# Запустить остановленный контейнер
docker compose -p lct -f compose.planner.yaml start
```

Контейнер ограничен **2 CPU / 1 ГиБ RAM**, работает от пользователя `node`, без привилегий и монтирования домашних каталогов. Порт привязан только к `127.0.0.1`. Базовый образ Node 24.14.1 закреплён digest, зависимости — `package-lock.json`. Имя проекта `-p lct` обеспечивает имя контейнера `lct-planner-1`, которое использует скрипт фиксации среды.

**Не открывайте этот API в интернет:** нет пользовательской авторизации и промышленной очереди заданий; у локального Wrangler сохранены ограничения обработки прерванных/медленных запросов.

## Локальная разработка без Docker

Рекомендуется **Node.js 24.14.1** и npm. На Windows используйте PowerShell 7. Проверенные команды выполняются из корня проекта:

```powershell
node --version
npm ci
npm run dev:planner
```

Адрес: **[http://127.0.0.1:3015/planner](http://127.0.0.1:3015/planner)**. Остановка — `Ctrl+C`. Для проверки сборки: `npm run build`.

Для расчётов не нужен `.env`. Файл `.openai/hosting.json` с пустыми локальными привязками нужен текущему конфигу сборки; внешние D1/R2 не используются. Версия `package.json` — техническая версия исходного шаблона, актуальную версию ядра проверяйте через health и `lib/planner/mission-schema.ts`.

## Что показать эксперту

1. Откройте «Сценарии» → **«Автовыбор БВС: время, налёт и баланс»**. Изучите паспорт: область, работы, окно, аппараты и допущения.
2. Нажмите «Рассчитать варианты». Сравните «Раньше закончить», «Меньше летать» и «Баланс»: время последней посадки, суммарный налёт, аппараты и вылеты.
3. Проверьте ограничения и неизвестные параметры. Подтвердите выбранную версию и запустите модельное проигрывание.
4. Измените состав флота, область, батареи или условия. Прежнее подтверждение сбросится; повторите расчёт. «Сохранить как» создаёт отдельный номер миссии.
5. Выгрузите полную миссию JSON/YAML, план GeoJSON/KML и «Доказательства» JSON. Отдельным инструментом повторно проверьте доказательства.
6. Покажите отрицательный сценарий: сильный ветер либо недостаточный ресурс. Система должна отказать, а не выдавать неполное задание за успешное.

В корпусе **9 синтетических сценариев / 36 входных файлов**: автоматический выбор БВС; смешанный флот RGB/MS/ИК; LiDAR/геофизика; повторные вылеты; временная зона; высотное препятствие; участок с отверстием; отказ по ветру; отказ по ресурсу. [Описание и готовые файлы](docs/planner/scenarios.md).

В сценарии компромисса на 0,42 км² сохранённый прогон дал: **23,4 мин** до завершения для быстрого плана, **21,4 мин суммарного налёта** для экономного и **26,3 мин / 23,6 мин** для баланса. Это разные метрики: параллельные полёты сокращают срок, но их налёт суммируется. Баланс выбирает допустимый найденный план с равными весами двух нормализованных показателей; глобальная оптимальность и физический износ не доказываются.

## Форматы и данные

| Файл | Для чего нужен |
| --- | --- |
| Полная миссия JSON / YAML 2.0 | Перенос, редактирование и повторный расчёт всего задания |
| Markdown | Читаемое описание; не формат обратного импорта |
| GeoJSON / KML на входе | Координатные области, границы, запреты и точки; не DEM |
| `prime-fleet` JSON 1.0 | Импорт профилей БВС и экземпляров батарей |
| `prime-restrictions` JSON 1.0 | Объёмы ограничений с высотами, временем и источником |
| GeoJSON / KML результата | План группы или аппарата с атрибутами; не проверенные команды автопилота |
| Evidence JSON | Вход, кандидат, проверки, события, хеши и подтверждение версии |

Контракт: [JSON Schema](docs/planner/contracts/mission-v2.schema.json). Учебные входы: [1 км²](docs/planner/contracts/example-1km2.json), [10 км²](docs/planner/contracts/example-10km2.json), [100 км²](docs/planner/contracts/example-100km2.json). Лимиты: 8 работ, 10 БВС, 100 батарей, 20 дополнительных ограничений; полное задание — до 200 КиБ UTF-8.

Библиотека заданий хранится **локально в браузере (IndexedDB)**. Порты 3015 и 3016 имеют разные хранилища. Очистка данных браузера может удалить записи — сохраняйте JSON/YAML и резервную копию библиотеки. Карта запрашивает тайлы OpenStreetMap и раскрывает провайдеру просматриваемую область; отключите подложку для работы без этих запросов. Расчётное ядро работает локально.

## Как проверить

Команды ниже не заменяют изучение отчётов: `pass` относится к объявленной модели, а `unknown` остаётся неизвестным. API/UI-проверки выполняйте последовательно при свободном стенде на порту 3016.

### 1. Типы и модульные тесты

После `npm ci`:

```powershell
npm run typecheck
npm run test:planner
```

`test:planner` запускает `tests/*.test.ts`, но **не** вложенную папку приёмки. В среде, где запрещено создание дочернего процесса Node, эквивалентный запуск без изоляции процессов:

```powershell
node --experimental-transform-types --experimental-test-isolation=none --test tests/*.test.ts
```

### 2. Восемь приёмочных проверок

Нужен работающий API на порту 3016; тест A8 обращается к нему, остальные используют локальные модули и синтетические данные:

```powershell
node --experimental-transform-types --experimental-test-isolation=none --test tests/acceptance/track5-readiness.test.ts
```

### 3. Реальный HTTP API, сценарии и доказательства

Новый прогон сохраняется отдельно от исторического среза 0.3.0:

```powershell
npm run verify:missions -- http://127.0.0.1:3016 output/recheck/api
node --experimental-transform-types scripts/capture-mission-runtime.ts output/recheck/api
npm run verify:evidence -- output/recheck/api/evidence-1km2.json output/recheck/api/independent-check.json
node --experimental-transform-types scripts/verify-mission-showcase.ts http://127.0.0.1:3016 output/recheck/scenarios
```

Первый скрипт проверяет HTTP-контракт, повторяемость, площади 1/10/100 км² и сохраняет результаты/экспорт. Скрипт среды требует Docker и по умолчанию контейнер `lct-planner-1`; другое имя/ID передаётся последним аргументом после каталога отчёта. Для dev-запуска без Docker его пропускают. Проверка evidence заново рассчитывает проверки сохранённого кандидата, а не доверяет записанным `pass`.

**HTTP 200 и успешный нагрузочный тест 100 км² не означают, что вся миссия решена:** в сохранённом срезе 1 и 10 км² решены, 100 км² возвращает `not_found`. Подробности — в `report.json`, статусах кандидатов и списках `fail` / `unknown`.

### 4. Браузерные проверки

Готовые сценарии: `scripts/verify-mission-browser.js` (основной цикл) и `scripts/verify-mission-showcase-browser.js` (галерея, флот, сохранение, импорт, сравнение, ограничения, мобильный экран). Они выполняют реальные действия и запросы, без подмены API.

Для них нужен **Playwright CLI 0.1.20** и установленный поддерживаемый браузер. CLI — отдельный QA-инструмент, не runtime-зависимость приложения. Команды ниже проверены с Microsoft Edge на Windows; для установленного Chrome замените `--browser msedge` на `--browser chrome`. Используйте новый отдельный профиль, а не свою рабочую библиотеку:

```powershell
New-Item -ItemType Directory -Force output/playwright/recheck-core | Out-Null
node --experimental-transform-types scripts/create-geometry-overflow-fixtures.ts
npx --yes --package @playwright/cli@0.1.20 playwright-cli -s=prime-core-qa open http://127.0.0.1:3016/planner --browser msedge
npx --yes --package @playwright/cli@0.1.20 playwright-cli -s=prime-core-qa run-code --filename scripts/verify-mission-browser.js --raw
npx --yes --package @playwright/cli@0.1.20 playwright-cli -s=prime-core-qa close
npx --yes --package @playwright/cli@0.1.20 playwright-cli -s=prime-features-qa open http://127.0.0.1:3016/planner --browser msedge
npx --yes --package @playwright/cli@0.1.20 playwright-cli -s=prime-features-qa run-code --filename scripts/verify-mission-showcase-browser.js --raw
npx --yes --package @playwright/cli@0.1.20 playwright-cli -s=prime-features-qa close
```

Скрипты запускаются **через CLI, не `node` напрямую**. Сводка возвращается в вывод CLI: сохраните её отдельно и проверьте все `checks`; у расширенного сценария также должны быть `status: "pass"` и `failure: null`. Код завершения CLI сам по себе недостаточен: расширенный сценарий возвращает отчёт и при ошибке.

Новые снимки и выгрузки пишутся в `output/playwright/recheck-core` и `output/playwright/recheck-showcase`, не затрагивая архив 0.3.0. Следующий повтор перезапишет одноимённые файлы **recheck**. Не добавляйте завершающий `;` после внешней стрелочной функции в этих сценариях. CLI скачивается отдельно; для строго повторяемой проверки зафиксируйте использованную версию CLI и браузера в новом отчёте.

## Границы решения

- **Рельеф:** неизвестный либо явно плоский. Нет DEM и достоверного преобразования AGL/AMSL; высота проверяется, но автоматически не оптимизируется.
- **Погода:** ручной постоянный ветер, облачность и видимость на окно, без прогнозного сервиса. Неизвестные данные не подменяются нулями.
- **Энергия:** линейная модель ресурса по воздушному времени. Нет калибровки по реальным полётным логам, температуре, массе и деградации АКБ.
- **Аппараты:** поддержанные мультироторные модельные профили; самолёт Геоскан 201 явно `unsupported` до отдельной модели его фаз.
- **Поиск:** ограниченная эвристика, не доказанный глобальный оптимум. `not_found` не доказывает невозможность любого плана. Скорость CPU может влиять на число рассмотренных вариантов.
- **Безопасность:** проверяются ограничения локальной модели; нет разрешений, живой воздушной обстановки, реальной телеметрии и сертификации. Отдельный валидатор использует общую геометрическую библиотеку и не является внешним независимым органом.
- **Экспорт:** совместимость с конкретным автопилотом и импортёром Geoscan не подтверждена. Качество фактической съёмки и аварийные сценарии требуют дальнейшей валидации.
