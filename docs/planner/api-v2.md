# API и форматы Planner

Рабочее ядро **0.4.0**, формат миссии **2.0**. Актуально для локального стенда на порту 3016. [Руководство](submission/INTERFACE-GUIDE.md) · [Схема](contracts/mission-v2.schema.json).

## Адреса

| Метод и путь | Назначение | Вход |
| --- | --- | --- |
| GET `/api/planner/health` | Версии и состояние | Без тела |
| POST `/api/planner/missions/solve` | Расчёт двух обязательных критериев | Полный документ миссии, до 200 КиБ |
| POST `/api/planner/missions/solve-with-obstacles` | То же с вложенными источниками | До 12 МиБ; основная миссия без вложений до 200 КиБ |
| POST `/api/planner/missions/analyze` | Стресс-проверка кандидата | `document`, `candidate`, необязательные `perturbations` |
| POST `/api/planner/missions/contingency` | Проверка защитного прекращения | Строго `{document, candidate}` |
| GET `/api/planner/weather?q=...` | Необязательный прогноз | JSON запроса в URL-параметре q; схема в [адаптере](../../lib/planner/weather-provider.ts) |

Для POST нужен `Content-Type: application/json`. Для analyze/contingency обычный лимит — 2 МиБ; с `x-prime-obstacles: 1` — 14 МиБ с сохранением лимита основной части. Каждый KML-источник ограничен 8 МиБ. Проверки схемы и геометрии заголовком не отключаются.

`/api/planner/solve` — прежний v1, не основной рабочий цикл. В health `missionEngineVersion` — версия этого движка; старое `engineVersion` относится к v1. `flightReady: false` означает отсутствие допуска к физическому управлению БВС.

## Пример расчёта

Из корня проекта, PowerShell 7:

```powershell
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:3016/api/planner/missions/solve' -ContentType 'application/json' -InFile 'public/planner/scenarios/demo-01-survey.mission.json'
```

HTTP 200 означает обработанный запрос, **не** автоматически успешную миссию. Смотрите статусы кандидатов и проверки.

Основные поля ответа: `document`, `inputHash`, `engineVersion`, `createdAt`, `computationMs`, `warnings`, `candidates`; при наличии допустимых решений — `recommendation`, исследование ресурсов — `resourceStudy`.

## Документ миссии

Имена и типы полей задаёт [схема](contracts/mission-v2.schema.json); дополнительные семантические проверки — [mission-schema.ts](../../lib/planner/mission-schema.ts).

- Координаты WGS84: долгота, широта. Расстояния/высоты — метры, скорость — м/с, относительное время — секунды.
- `window.start/end` — ISO 8601 со смещением; `timezone` — IANA-пояс. Длина окна — до семи суток.
- `jobs[]` — до восьми записей работ/участков; отдельное `window` должно лежать внутри окна миссии. Работа содержит геометрию, параметры сенсора, высоту, освещённость, назначенные БВС.
- `jobs[].quality.altitudeMode`: `fixed` или `gsd`. При GSD нужны размеры сенсора/кадра, фокус и `maximumGsdCm`. Отсутствие этих данных не заполняется выдуманными измерениями.
- `bases[]` — до 40 баз; необязательные `landingPads` задают отдельные места, совместимый тип БВС и доступность. Центр базы сам по себе не доказывает безопасную вместимость.
- `planning.maxVehicles` — до 20 различных аппаратов за всю миссию, не число одновременно летящих.
- `planning.maxComputeMs` — бюджет поиска 100–30 000 мс. Это мягкий бюджет между попытками, не жёсткий предел длительности каждого геометрического шага.
- Текущие модельные политики: `batteryPolicy: installed-current-v1`, `safetyPolicy: continuous-occupancy-v1`, `areaTransferPolicy: compatible-work-v1`.
- Новый расчёт требует текущей политики безопасности; отсутствие даёт 422 `SAFETY_POLICY`. Исторический вход не меняется незаметно ради прохождения проверки.
- `maintenance` у БВС хранит наработку аппарата отдельно от заряда батареи. Отсутствующий счётчик не равен нулю.
- `environment` задаёт облачность/видимость в принятой локальной системе; `weather` — отдельный снимок прогноза. Их наличие не означает физического измерения.
- Необязательное `airspaceAltitudeReference` задаёт пересчёт FL: `standard-atmosphere`, `pressure-altitude-offset` с `offsetM/uncertaintyM` или `unknown`. В каждом варианте нужен `source`. При отсутствии поля применяется явно обозначенная модель ISA; исторический документ автоматически не дописывается. [Определение поправки и примеры](expert-materials/2026-09-23/zone-rules.md#высотная-привязка).

Высоты всех фаз проверяются строго ниже 150 м над принятой поверхностью. Автоматическая высота ограничена минимумом GSD-высоты, потолка миссии и 149 м. Это правило модели трека; реальный AGL без DEM не установлен.

## Слои и общий парк

`obstacleLayer` содержит адаптер `geoscan-kml-horizontal/1`, имя, неизменный `sourceText`, буфер и происхождение правил. Обход KML-препятствий горизонтальный. Каталоги участков/зон сохраняются в `catalogLayers`; правила зон — отдельно от исходного текста. При превышении бюджета — отказ, не усечение.

Высоты зон читаются из `Altitudes`, с отдельной системой отсчёта каждой границы. Расписание и высота независимы: отсутствие расписания не расширяет известный диапазон до земли. В ZIP `data/restrictions/normalized.json` версии 2.0 сохраняет исходные границы, текстовые условия, модель пересчёта и применённый диапазон. Исходный KML сохраняется отдельно и повторно проверяется при верификации архива. [Полные правила](expert-materials/2026-09-23/zone-rules.md).

`fleetSnapshot` связывает версии общего парка; `resourceReservations` — снимок занятости другими запусками, не живая телеметрия.

`jobs[].inheritsFrom` связывает параметры участка того же вида работ: циклы/цепочки запрещены, геометрия и название не наследуются. `revisionSource` связывает пересмотр миссии с исходным запуском и покрытием. Импорт файла без нужной исходной истории сам по себе не разрешает такой запуск.

## Статусы и выбор

| Статус кандидата | Значение |
| --- | --- |
| `feasible_model` | Полный план прошёл обязательные проверки объявленной модели |
| `partial` | Часть обязательных работ не выполнена |
| `not_found` | Ограниченный поиск не нашёл допустимый план |
| `invalid` | План нарушает проверки |
| `unsupported` | Конфигурация не поддержана |

Два основных кандидата: `makespan` и `flightTime`. Дополнительный ID `balanced` использует **`deadline-min-flight-v1`**: минимум налёта среди найденных допустимых планов к сроку и в лимите БВС. При равенстве — раньше завершить, больше остаток, меньше вылетов. Прежняя формула 50/50 больше не действует. Совпадение с основным планом отмечается явно.

`resourceStudy` различает `found`, `not_found`, `not_searched`. Непроверенное число ресурсов не считается доказанно недостаточным.

Вылеты содержат назначения, фазы, времена, скорости, высоты и энергию. `makespanSec` — до последней посадки; `flightTimeSec` — сумма времени в воздухе. Покрытие территории не равно прогрессу воспроизведения.

## Ошибки и эксплуатация

400 — JSON/схема; 403 — Origin; 408 — время чтения тела; 413 — размер; 415 — Content-Type; 422 — семантика/вычисление; 429 — занят обработчик. Проверка Origin не является аутентификацией.

Отмена запроса в браузере не гарантирует мгновенную остановку серверного CPU. [HTTP-вход и его границы](http-ingress.md). Не публиковать текущий loopback-стенд в интернет без отдельной защиты и эксплуатационной проверки.

## Проверка результата

Основной формат для эксперта — ZIP: [состав и команды](submission/EXPERT-FILES.md).

```powershell
node --experimental-transform-types scripts/verify-mission-archive.ts "путь/миссия.evidence.zip"
```

CLI проверяет хеши и заново оценивает сохранённый кандидат. Отдельный проход использует общую с решателем геометрическую библиотеку, поэтому не является внешней сертификацией.

Повторный поиск может дать другой вариант на другом CPU при ограничении времени. Для проверки именно полученного результата используйте сохранённый `plan/candidate.json`.

Дополнительные технические инструменты: `verify-mission-run-report.ts` для JSON запуска, `verify-mission-evidence.ts` для прежнего evidence.json, `verify-mission-contingency.ts` для протокола защитного прекращения. Они не подменяют проверку полного ZIP.
