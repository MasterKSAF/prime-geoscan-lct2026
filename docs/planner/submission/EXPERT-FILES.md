# Эксперту: какие файлы скачать и как проверить

Planner **0.4.0**, 25 сентября 2026 года. [Запуск стенда](../../../README.md#запустить) · [Короткая ручная проверка](MANUAL-REVIEW.md).

## Источники требований

[Письменное ТЗ](../../geoscan-md/geoscan-track5-tz.md), разделы 2, 4, 5, 7: индивидуальные KML/GeoJSON для каждого БВС, две цели оптимизации, код/демо/презентация/документация и инструкция запуска. [Резюме уточнений 23.09](../expert-materials/2026-09-23/planning-answers.md) указывает на самостоятельную проверку экспертами, но не задаёт отдельную схему JSON-проверок. Веса и автоматический официальный оценщик не предоставлены. ZIP ниже — наш воспроизводимый комплект, не выдуманный стандарт организатора.

## Где скачать

| Экран и кнопка | Файл | Что внутри |
|---|---|---|
| Проверка перед загрузкой → Скачать миссию → JSON | `.mission.json` | Полный вход для повторной загрузки |

| Выполнение → Скачать миссию | `.mission.json` | Снимок именно выбранного запуска, не текущий черновик редактора |

| Выполнение → Отчёт миссии | Переход в Отчёт | Все выгрузки результатов |
| Редактор → Данные миссии → Скачать данные миссии JSON | `.mission.json` | Рабочий вход со всеми изменениями и слоями; это не снимок завершённого полёта |
| Отчёт → Открыть отчёт | Просмотр в стенде | Результат выбранной строки, а не другой миссии в редакторе |
| Отчёт → Все проверки | Анализ в стенде | Непройденные проверки, причины и дальнейшие действия |
| Отчёт → Скачать маршруты → KML / GeoJSON | `.routes-kml.zip` / `.routes-geojson.zip` | Файлы каждого назначенного БВС и краткий README; только для допустимого плана |
| Отчёт → Другие файлы | `.report.html`, `.checks.json`, готовый `.mp4` | Отдельные отчёт, проверки и видео |
| Отчёт → Доказательства ZIP | `.evidence.zip` | Полный переносимый комплект, включая KML/GeoJSON |

## Что смотреть внутри ZIP

| Путь относительно `data/` | Назначение |
|---|---|
| `README.md` | Порядок проверки и команда |
| `report.html` | Начать здесь: результат и ограничения |
| `input/mission.json`, `input/mission.html` | Точный вход и паспорт |
| `plan/candidate.json` | Выбранный план, точные времена и сегменты |
| `routes/<БВС>.kml`, `.geojson` | Полётное задание каждого назначенного аппарата по ТЗ |
| `checks/validation.json` | Геометрия, полнота, батареи, ветер, временные окна, разнесение, целостность экспорта |
| `checks/recovery-preflight.json` | Отдельная модельная проверка защитного возврата |
| `checks/requirements.json` | Связь проверок с доказательствами; не официальная балльная матрица |
| `analysis/resources.json` | Расход ресурса, налёт по фазам, ТО |
| `run/report.json`, `run/events.jsonl`, `run/control-events.json` | Итог запуска, события и действия оператора; только если был запуск |
| `sources/`, `obstacles/`, `restrictions/` | Исходные слои, хеши, принятые объекты и применённые ограничения |
| `restrictions/normalized.json`, `restrictions/applied.json` | Каждая зона: исходная строка, обе системы высот, пересчёт относительно поверхности, модель давления, расписание и реально применённые объёмы; нормализация версии 2.0 |
| `simulation/` | Модельный опрос/погода/материалы, не реальные полётные измерения |
| `reproduce.json` | Версия, хеш входа, бюджет и границы оптимизации |

Корневые `manifest-sha256.txt` и `tagmanifest-sha256.txt` обнаруживают изменение файлов, но не являются электронной подписью. Высоты в KML — в ExtendedData, в GeoJSON — в свойствах с явно указанной системой отсчёта; не угадывать AMSL по линии на карте.

`bagit.txt` и `bag-info.txt` описывают упаковку. Таблица выше относится к допустимому плану; `run/` появляется после запуска, `sources/` и производные каталоги — при соответствующих входных слоях. Диагностический ZIP содержит `data/diagnostic.json`, вход, кандидата, проверки, отчёт и происхождение, но не успешные `routes/` и `run/`. Архив не требует вымышленных пустых файлов для отсутствующих источников.

## Состав индивидуального полётного задания

Сверено с [реальным экспортёром](../../../lib/planner/mission-export.ts). Файлы разделяются по `vehicleId`; если одному БВС назначено несколько вылетов, все они входят в его файл. Требование ТЗ «KML/GeoJSON» реализовано выдачей обоих форматов.

| Требование §2 ТЗ | Где искать в KML | Где искать в GeoJSON |
|---|---|---|
| Назначенный БВС и работа | `Folder/ExtendedData`: `vehicleId`, `sortieId`, `jobId`, `batteryId`; этапы внутри вылета | `properties` объектов `sortie`/`segment`: те же ID; у вылета также `jobIds` |
| Маршрут и ключевые точки | Последовательные `Placemark/LineString`; `from`/`to` этапов в `ExtendedData` | `LineString` вылета и сегментов; объекты `Point` с `kind: waypoint` для концов этапов. Начальная точка — `from` первого сегмента |
| Высоты и система отсчёта | `altitudeFromM`, `altitudeToM`, `altitudeDatum` в `ExtendedData` | Свойства сегмента с теми же полями; у ключевой точки — `altitudeM`, `altitudeDatum` |
| Скорости | `airspeedMps`, `groundSpeedMps` у каждого этапа | Те же поля у сегментов и точек; единицы м/с объявлены на уровне коллекции |
| Старт и посадка | Начало взлётного/конец посадочного этапа соответствующего вылета; координаты `from`/`to` | Те же этапы по `phase`, координаты сегментов и ключевых точек |
| Последовательность этапов | `sequence`, `phase`, `startSec`, `endSec`; `TimeSpan` | `sequence`, `phase`, относительные секунды и абсолютные `startTime`/`endTime`; у точки — время достижения |
| Привязка к входу | `missionId`, `candidateId`, `inputHash`, `schemaVersion`, `flightReady` в документе | Те же свойства коллекции, дополнительно `engineVersion`, единицы и модель поверхности |

Координаты записаны в порядке **долгота, широта** (WGS84). KML использует `clampToGround`, координаты линии имеют нулевую третью компоненту: это проекция для карты. Рабочая высота хранится отдельно в `ExtendedData`. GeoJSON также не подменяет модельную высоту недоказанной абсолютной отметкой. `above_declared_local_flat_surface` означает высоту над объявленной плоскостью; `unverified_relative_height` — неподтверждённую относительную высоту.

KML показывает ключевые точки как концы этапов, без отдельных точечных `Placemark`; GeoJSON содержит явные `Point`. Для семантической проверки обоих форматов используйте проверщик архива, а не только внешний просмотрщик линии. Это описательное модельное задание с `flightReady: false`; совместимость с командами конкретного автопилота не утверждается.

## Независимый запуск проверки

Из корня проекта после `npm ci`, Node.js 24:

```powershell
node --experimental-transform-types scripts/verify-mission-archive.ts "C:/путь/миссия.evidence.zip"
```

Результат `passes-declared-model` и код 0 означают, что архив цел и сохранённый план заново прошёл модельные проверки. При нарушении — код 1. `unknown` не превращается в `pass`: физические измерения не получены. Отдельно смотрите статус резервного возврата и статус выполнения самой миссии. Валидный план ещё не означает завершённое выполнение, а успешные проверки безопасности не доказывают оптимальность.

У Демо 3 до исправления входа скачивается **диагностический** ZIP: `diagnostic-only-not-flight-approved` и код 1 означают воспроизведённый отказ плана. У архива события — `incident-diagnostic-reproduced`, также не допуск к полёту. Эти статусы не равны повреждению архива; ошибка хешей/содержимого сообщается отдельно. В диагностике нет вымышленных успешных маршрутов или завершённого запуска.

Для проверки именно поиска загрузите `input/mission.json` в редактор и рассчитайте оба критерия. Для проверки независимости от демо измените территорию, парк, заряд или срок и повторите расчёт. Перед изменением сохраните исходный файл. Разные CPU при временном бюджете могут найти разные допустимые планы — для точного воспроизведения результата проверяйте сохранённый кандидат.

## Достаточность

По составу ZIP включает выходные маршрутные файлы, предусмотренные ТЗ, и расширенный проверочный набор. Сдача также требует кода, рабочего демо, актуальных документации и [презентации](presentation/README.md), доступных экспертам ссылок. Наличие ZIP само по себе не означает готовность всей сдачи или максимальный балл. [Что и куда загрузить](SUBMIT.md).
