# Самостоятельная приёмка Planner 0.4.0

Методика команды **ПРАЙМ**, обновлена 25.09.2026. Основание — [ТЗ](../../geoscan-md/geoscan-track5-tz.md), разделы 2–5 и 7; это проверка программного результата, не официальный акт жюри и не натурные испытания. Сведения о фактическом прохождении заносятся отдельно в протокол.

## 1. Условия и протокол

1. Запустить стенд по [README](../../../README.md), открыть `http://127.0.0.1:3016/planner` в современном браузере на ПК. Записать дату, ОС, браузер, версию Node/Docker, commit либо хеш комплекта и ответ `/api/planner/health`.
2. Сохранить нужные данные прежней сессии; создать отдельную проверочную сессию и выполнить «Настройки → Начать с нуля». Во время сценария не обновлять страницу.
3. Для проверки ZIP установить зависимости через `npm ci`. Команды проверки выполняются из корня проекта; образ Docker использует Node.js 24.
4. Для каждого пункта записать `пройден / не пройден / не выполнен`, фактический результат и ссылку на доказательство. Серая кнопка с объяснимым предусловием — проверяемое состояние, а не автоматически дефект. Наличие метода или теста в коде не означает ручного прохождения.

Рекомендуемые поля протокола: `ID проверки; дата; версия и вход; действия; ожидание; факт; статус; файл/хеш доказательства; проверяющий`. Не заполнять имя или подпись эксперта автоматически. [Короткий лист](MANUAL-REVIEW.md) можно использовать как бумажную форму.

## 2. Обязательные три сценария

| ID | Действия | Критерий успешной программной проверки | Сохраняемые результаты |
|---|---|---|---|
| S1 — простая съёмка | Демо 1 → редактор → «Рассчитать варианты». Сравнить «Быстрее закончить» и «Меньше налёт» на одном входе. Выбрать допустимый план, подтвердить, выполнить до конца, открыть отчёт | Для выбранного плана нет блокирующих нарушений; показаны время завершения и сумма налёта, назначенные БВС, карта и отдельный журнал. Проходы и площадь показаны раздельно | JSON входа; KML/GeoJSON всех назначенных БВС; полный ZIP с журналом. Проверщик ZIP возвращает `passes-declared-model`, код 0 |
| S2 — слои экспертов | Демо 2 → показать источники участков/зон/препятствий → рассчитать оба критерия → проверки → подтвердить → выполнить → отчёт | Участки и препятствия взяты из сохранённых источников, обход и разнесение проходят модельные проверки. Покрытие сравнивается с числом отчёта, а не округляется вручную до 100% | Точный вход, оба набора индивидуальных маршрутов и ZIP. В `sources/`, `obstacles/`, `restrictions/` сохранены происхождение и правила |
| S3 — отказ | Исходное Демо 3 → рассчитать → «Все проверки» → скачать диагностический ZIP | Подтверждение/запуск недопустимого плана заблокированы. Причины и предлагаемые изменения понятны. В архиве нет успешных маршрутных заданий и завершённого журнала | JSON входа, диагностический ZIP. Ожидается `diagnostic-only-not-flight-approved`, код 1. Ошибок целостности быть не должно |

S1/S2 принимаются по конкретному сохранённому кандидату: ограниченный временем поиск на другом CPU может выбрать другой допустимый вариант. Два критерия могут совпасть; это не основание требовать искусственно разные маршруты. `passes-declared-model` относится к проверке плана; завершение запуска проверяется отдельно в отчёте.

В S2 исходные каталоги содержат 696 участков, 341 зону и 5 164 препятствия. Демо использует два контура, несколько работ и четыре ближайших препятствия. На выбранной небольшой территории нет пересекающих каталожных зон: S2 не доказывает сам по себе обход действующего запрета. Базы, парк, погода, время и поверхность — модельные условия.

**S2-Z — контроль воздействия запрета:** сохранить S2, загрузить копию с новым ID, добавить запрет на всю область полёта, весь используемый диапазон высот и всё окно миссии. Новый расчёт должен отказать в допуске. Удалить добавленный запрет и пересчитать; допустимость должна восстановиться при неизменных остальных ресурсах. Это искусственный тест ограничений, не изменение разрешений организаторов.

**S3-R — контроль исправления:** сохранить исходный отказ, создать копию и внести рекомендованное изменение ресурсов/срока. Пересчитать. Приёмочный критерий — корректная новая диагностика; успех объявляется только после положительных проверок, а не по факту редактирования поля.

## 4. Приёмка выходных файлов

1. Сопоставить `missionId`, `candidateId`, `inputHash`, версию и список назначенных БВС с отчётом. В каждом формате должно быть индивидуальное задание каждого назначенного аппарата; неиспользованный БВС не требует фиктивного маршрута.
2. Проверить маршрут, ключевые точки, высоты и их основу, скорости, старт/посадку и порядок фаз по [точной таблице полей](EXPERT-FILES.md#состав-индивидуального-полётного-задания). Линия на карте без этих данных недостаточна.
3. Сверить отдельные маршрутные ZIP с `data/routes/` полного ZIP. Открыть `data/report.html`; сравнить показатели покрытия, прохождения и фактический статус выполнения.
4. Запустить `node --experimental-transform-types scripts/verify-mission-archive.ts "путь/миссия.evidence.zip"`. Проверить полный JSON результата и код завершения; для S3 ожидается код 1 с диагностическим статусом, без ошибки целостности.
5. Убедиться, что S2 сохраняет исходные каталоги и правила нормализации. Если запуска не было, отсутствие `run/` нормально; для завершённого S1/S2 журнал обязателен. MP4 — отдельная выгрузка, не обязательное содержимое ZIP.

## 5. Решение по результатам

Основной проход выполнен, когда S1/S2 подтвердили полный модельный путь с корректными файлами, S3 подтвердил воспроизводимый отказ, а остальные выполненные пункты имеют записи. Непройденные/невыполненные UI-пункты и внешние ограничения фиксируются явно. Автор методики не ставит итоговую подпись за принимающую сторону. Программный результат нельзя переносить на лётную годность, действительность разрешений или качество настоящей съёмки.
