# Понятный путь от задачи до доказанного плана

**Идея:** пользователь объясняет, что нужно сделать, через последовательные вопросы и карту. Система переводит ответы в строгую задачу, рассчитывает варианты, объясняет различия и ждёт подтверждения выбранного плана. Это структурированный диалог, не чат, который сам додумывает координаты, безопасность или тип сенсора.

Основание: [ТЗ](../geoscan-md/geoscan-track5-tz.md), [встреча](meetings/2026-09-16-full/summary.md), [исследование норм/профилей](standards-profiles-and-missions.md), пожелания пользователя 17.09. Этот документ задаёт будущие функции. Наличие описания не означает, что они уже работают.

## 1. Три разных объекта

| Объект | Что содержит | Кто изменяет |
| --- | --- | --- |
| Задача миссии | Где/когда/какие работы, требуемое качество, доступный парк, ограничения и предпочтения | Оператор через мастер либо импорт |
| Рассчитанный план | Назначенные БВС/батареи, вылеты, маршруты, события датчиков, времена, ресурс и проверки | Решатель; затем неизменяемая версия |
| Прогон симуляции | Воспроизведение выбранного плана, позиции, состояния и журнал событий | Модель стенда, не реальное БВС |

Название кнопки «Запустить» уточнить: **«Начать симуляцию»**. Реальных команд на вылет в этом MVP нет. Дата задания влияет на расчёт расписания, но не запускает физический аппарат автоматически.

## 2. Мастер «Новая миссия»

| Шаг | Вопрос системы | Ввод и помощь |
| --- | --- | --- |
| 1. Работы | Что нужно получить? | Выбор RGB/MS/ИК/LiDAR/геофизики из каталога. Для каждой работы — только необходимые параметры качества. Краткая подсказка без терминов; подробности по кнопке |
| 2. Территория | Где выполнить работу? | Нарисовать область, выбрать сохранённую, загрузить GeoJSON/KML. Несколько областей и отверстия сохраняются. Область работ и область разрешённых полётов — разные слои |
| 3. Срок | Когда можно работать? | Дата, часовой пояс, начало/конец окна; по желанию жёсткое время старта или крайний срок. Прибор/тип работ задаёт дополнительные условия времени |
| 4. Ресурсы | Чем и откуда выполнять? | БВС с конкретными сенсорами, батареи, старт/посадка/резервные площадки, время готовности. По умолчанию распределить автоматически; можно исключить БВС или закрепить работу за совместимым аппаратом |
| 5. Ограничения | Где и при каких условиях нельзя лететь? | Разрешённые объёмы, запреты со сроками, препятствия, ветер, высоты/система отсчёта, минимальные интервалы. Загрузка слоёв или редактор. Источник и неизвестные данные видимы |
| 6. Предпочтения | Что важнее? | Закончить раньше / меньше суммарно летать. Необязательно: предпочитать ниже/выше в допустимом диапазоне, сторону обхода, выбранную базу |
| 7. Проверка задания | Всё понято правильно? | Краткая карточка и полное описание, карта слоёв, допущения/ошибки, список возможных комплектаций. Кнопки «Изменить», «Сохранить задачу», «Подтвердить и рассчитать» |

Мастер не должен требовать вручную распределить всё по БВС: это задача алгоритма. Для закреплённого назначения конфликт объясняется, а не обходится скрытым использованием другого аппарата.

Текстовый комментарий оператора допускается, но **не изменяет расчёт**. Если позднее появится ввод обычной фразы, он только создаёт черновик тех же полей; пользователь подтверждает структурированные значения. LLM и GPU для первой версии не нужны.

## 3. Как предложить варианты и получить подтверждение

**Черновик → проверено → рассчитаны варианты → просмотр → подтверждённый план → симуляция.** Отдельные состояния: есть ошибки, данных недостаточно, поиск прерван, результата за бюджет нет, найдено частичное покрытие, конфликт доказан в рамках модели.

Карточки вариантов показывают одинаковый вход, все использованные ресурсы, окончание работ, суммарный налёт, число вылетов/замен, покрытие/качество, минимальные остатки, pass/fail/unknown. Первый вариант оптимизирует время окончания, второй — налёт. При совпадении честно показываем совпадение, не рисуем разную выгоду.

Кратко: «Два БВС, три вылета; окончание 14:35; одна замена АКБ; неизвестная высота одного препятствия». Полно: назначения, фазы, высоты, расчётные условия, нарушения и пути их устранения. Любая цифра здесь — пример интерфейса, не результат существующего прогона.

Подтверждение хранит ID/хеш выбранного входа и плана, версию профилей/правил и время подтверждения. Изменение геометрии, даты, ветра, сенсора или ограничений делает подтверждение недействительным. Ранее подтверждённая версия остаётся в истории, но не подставляется как актуальная.

## 4. Библиотека задач

Карточка: название, типы работ, территория/площадь, дата и статус, последняя правка, количество БВС, предупреждения. Действия: кратко / полностью / открыть копию / выгрузить / архивировать с подтверждением. Различать «сохранённая задача» и «сохранённый рассчитанный план».

Первый вариант — локальное хранилище браузера (IndexedDB) с явным уведомлением: данные привязаны к этому браузеру и могут быть удалены очисткой. Импорт/экспорт файла обязателен как резерв. На защите импорт на чистом браузере должен работать без старой базы. Серверную общую библиотеку добавлять отдельно при потребности, с постоянным томом и контролем доступа; не создавать её молча как облачный сервис.

При открытии файла или версии сначала предпросмотр: что добавится/изменится, источник координат, неизвестные поля/значения. Никакой перезаписи текущей несохранённой задачи без подтверждения.

## 5. Загрузка карт и понятный текстовый формат

| Формат | Назначение первой версии | Чего он не гарантирует |
| --- | --- | --- |
| `*.mission.yaml` | Читаемое описание задания с версией схемы; форма и файл взаимно преобразуются | Произвольный русский рассказ не является исполняемой задачей |
| `*.mission.json` | То же задание, каноническая машинная форма и интеграция API | Не путать с уже существующей схемой scenario v1: нужен явный адаптер |
| GeoJSON/KML | Области работ, точки площадок, разрешённые/запрещённые зоны, препятствия; при импорте выбрать назначение слоя | Чужой KML не содержит автоматически все расписания/семантику нашей миссии |
| `mission-summary.md` | Читаемое краткое и полное задание, параметры, допущения, список файлов | Не канонический обратный импорт; правка пересказа не меняет план |
| `plan.json` + индивидуальные KML/GeoJSON | Рассчитанный неизменяемый план и требуемая ТЗ выдача по каждому БВС | Не проверенная команда реальному автопилоту |
| DEM / геопривязанный растр | В первом ядре — документированный локальный адаптер высот; растровая подложка отдельным этапом | Не поддержка всех GIS-форматов и не автоматическое распознавание препятствий на фото |

**Выбор для YAML:** один документ, строковые ID и даты, конечные числа, явные единицы, ограниченный набор ключей. Запрет пользовательских тегов, ссылок/алиасов, исполняемых выражений; лимиты размера, вложенности, точек и объектов. Неизвестные ключи/неподдержанная версия — адресная ошибка, не тихая потеря смысла. Входной HTML экранируется. XML KML без DTD/внешних сущностей/сетевых ссылок; никаких серверных загрузок произвольного URL, абсолютных путей или файлов вне выбранного набора.

**Концептуальная форма будущего файла** — не готовый импорт текущей версии 0.1:

```yaml
schema_version: "2.0-draft"
mission_id: "survey-01"
name: "Съёмка участка"
timezone: "Europe/Moscow"
window:
  start: "2026-09-24T10:00:00+03:00"
  end: "2026-09-24T16:00:00+03:00"
objective: "min_completion_time"
layers_file: "site.geojson"
profile_set: "demo-v1"
jobs:
  - id: "rgb-01"
    type: "RGB"
    area_ref: "area-01"
    quality_profile: "rgb-demo"
    assignment: "auto"
constraints_profile: "demo-separation-v1"
```

Ключи — стабильные технические названия, подсказки и выгрузка описания — по-русски. `demo-*` ясно означает учебные значения. Это только фрагмент структуры: полного профиля, площадок, флота и геометрии здесь нет, такой файл нельзя объявлять готовым к расчёту. Окончательную схему закрепить перед реализацией по E01. Для автономного обмена экспортировать самодостаточный JSON/YAML со встроенными слоями/профилями; внешние файлы — дополнительный явный режим, не обязательная сложность.

Проверки обмена: экспорт → очистка библиотеки/новый браузер → импорт → те же нормализованные поля, координаты, единицы и хеш; затем одинаковый результат при одинаковом seed/бюджете. Комментарии/порядок YAML не участвуют в каноническом хеше. Чужой неподдержанный слой не теряется молча.

## 6. Реалистичная 2D-симуляция без подмены реальности

Стенд воспроизводит **один утверждённый расчётный план**, а не отдельную декоративную анимацию. Пауза/перемотка/ускорение меняют только модельное время. Общая шкала показывает подготовку, взлёт, переход, работу сенсора, возврат, посадку, обслуживание и следующий вылет. Для самолёта — его фазы, без зависания.

Карта: выполненные/оставшиеся полосы, активные запреты, позиции БВС, доступные посадки. Панель выбранного аппарата: задача/сенсор, высота и система отсчёта, скорость, остаток ресурса, ближайшее событие. Профиль высот остаётся плоским графиком; 3D не нужен.

Журнал: timestamp, mission/plan/run ID, БВС/батарея, фаза, событие, источник состояния, причина перехода. Модельный кадр/измерение — планируемое событие, не реально полученный файл. Замена АКБ меняет экземпляр батареи, не восстанавливает заряд старой магически.

Дополнительный сценарий стенда: оператор меняет ветер/активирует запрет → прежний план получает предупреждение/теряет актуальность → новый расчёт → новое подтверждение. Это **перепланирование сценария**, не обещание управления летящим БВС в реальном времени. Погоду по API, реальную телеметрию и автоматические команды не добавлять без отдельного задания.

## 7. CPU и ограничения запуска

17.09 локально определены AMD Ryzen 5 7430U, 6 физических ядер/12 логических потоков, около 13,8 GiB доступной ОС памяти. Текущий `compose.planner.yaml` ограничивает приложение **2 CPU и 1 GiB**. Это не вся мощность компьютера.

Начать с текущего TypeScript/геометрического ядра и строгих эталонов. Тяжёлый поиск изолировать от UI; для имеющегося серверного runtime сначала проверить доступный механизм вычислений, не обещать `worker_threads` там, где они не поддерживаются. При необходимости — отдельный CPU-процесс/контейнер с документированным контрактом. Не мигрировать весь стек заранее.

Сравнить 2/4 доступных CPU и ограниченные конфигурации памяти на одних сценариях; не менять лимиты стенда молча. Бюджет времени, отмена, предел геометрии, один расчёт одновременно по умолчанию. Измерять cold/warm, время, пиковую память, число кандидатов и статус качества. GPU/облачная LLM не являются зависимостью. Размер парка и скорость заявлять только после измерений.

## 8. Порядок поставки и доказательства

1. Схема v2, совместимость v1, каталог профилей/правил, импорт геометрии и адресные ошибки.
2. Сквозной мастер → задача → оба варианта → подтверждение → 2D-проигрывание → экспорт. Библиотека и обратный импорт без потери данных.
3. Временные окна/освещённость, 4D и разнесение, повторные вылеты и батареи; независимые проверки. Эти ограничения влияют на расчёт, не только на форму.
4. Завершение охвата ТЗ, эталоны/benchmark, чистый Docker, инструкция, слайды/скринкаст одной версии. Дополнительный погодный API, произвольный естественный язык, 3D и сложная зарядная инфраструктура — позднее.

Расширить существующую матрицу **E01–E16**, не выдавать новые ID за новую официальную оценку:

- E01/E11: мастер и YAML/JSON round-trip, v1→v2, неверные файлы/версии/единицы, XSS/XXE и размеры.
- E03/E09: граница окна съёмки, смена даты/часового пояса, неизвестные высоты, подтверждённые правила разных профилей; не применять RGB-правило ко всем сенсорам.
- E04/E05: междукадровое сближение, запрещённый путь на резервную посадку, ограничения на фазах взлёта/посадки.
- E06/E10: два вылета, фактическая доступность батареи, нулевое обслуживание, очередь последовательного зарядника если он заявлен; модельный цикл не меняет реальный счётчик.
- E12: несохранённое задание, preview/confirm, stale после правки, восстановление библиотеки, плеер соответствует плану, работа без карты/сети.
- E13–E16: лимиты CPU/памяти, чистая установка/импорт, замеры, живое демо и видео того же release ID, все неудачные/непроверенные проверки сохранены.

**Показ жюри:** загрузить новое задание → просмотреть смысл → рассчитать два варианта → объяснить выбор → подтвердить → проиграть вылет/замену/следующий вылет → изменить ограничение и показать объяснимый перерасчёт → выгрузить индивидуальные задания и доказательства. Видео — страховка и иллюстрация, не замена работающего веба.
