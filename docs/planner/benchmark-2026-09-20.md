# Измеримая эффективность и проверка экспертами

Протокол `same-input-serial-v1`, 20.09.2026. Это сравнение внутри нашей объявленной модели, **не сравнение с продуктами конкурентов, не доказательство глобальной оптимальности и не сертификация полётов**.

## Что измеряется

Сравниваются наш ограниченный поисковый алгоритм и простой последовательный алгоритм: первый подходящий аппарат и не более одного вылета в воздухе одновременно. Оба получают **тот же полный вход и его SHA-256**: исходные участки, все работы, парк, установленный заряд, требования качества, зоны, ветер и интервалы безопасности. Базовый алгоритм не получает дополнительные батареи, облегчённую задачу или ослабленные ограничения.

Сохраняются полные маршруты обеих сторон. Каждый маршрут повторно проверяет валидатор, а не только статус HTTP или сохранённая зелёная отметка. Экономия считается только для пары полных допустимых результатов. `partial`, `not_found`, `invalid`, `unsupported` остаются в отчёте, но не приносят «экономию» за невыполненную работу. `not_found` не доказывает математическую невозможность.

Два обязательных показателя считаются отдельно:

- **Время завершения всех работ:** до последней посадки, с подготовкой и ожиданиями.
- **Суммарный налёт:** сумма длительностей всех вылетов. Не физический износ оборудования.

Разница = базовое значение − наше значение. Процент = разница / базовое значение × 100. Отрицательные значения не скрываются. Нулевой знаменатель не превращается в бесконечный процент.

## Набор и воспроизводимость

15 заранее определённых входов: девять демонстрационных примеров, четыре варианта фиксированной сетки ветер/направление/заряд и два нагрузочных входа 10/100 км². Неудачные варианты сетки не удалены. Координаты привязаны к карте, но задачи, рельеф и профили синтетические. Это не закрытый набор экспертов и не статистически представительная выборка рынка. Случайный генератор не используется; `seed: null` указан явно.

По умолчанию выполняются три повтора каждого входа — 45 запусков, по два критерия. Повторы нужны для наблюдения разброса времени, а не для увеличения числа независимых задач. Один предварительный прогрев исключён из статистики. Порядок «наш → базовый» / «базовый → наш» чередуется.

Бюджет основного поиска — 2000 мс на обе цели; последовательного — 1000 мс на каждую. Это лимит поиска, а не обещание жёсткого ограничения всей длительности вызова. Таймер вызова включает встроенную проверку решателя. Дополнительный повторный проход валидатора и экспорт доказательств выполняются вне этого таймера. Оба алгоритма используют общий генератор маршрутов и часть общей геометрии: базовый метод — контрольная точка, а не независимая сильная конкурирующая система.

В отчёте сохраняются Node/Windows/CPU/память, пользовательское + системное процессорное время, реальное время вызовов, все исходные задания, кандидаты, их хеши и хеши исходников. `p50`/`p95` — перцентили методом ближайшего ранга. На Windows короткое процессорное измерение может округлиться до 0 мс; это не отсутствие вычислений.

Входы воспроизводимы побитно после канонизации JSON. Времена, временные метки и пул поиска при ограничении по часам могут отличаться на другом CPU. SHA-256 связывает файлы, но не удостоверяет личность автора и не доказывает правильность алгоритма.

## Команды

Из корня проекта, после `npm ci`:

```powershell
node --experimental-transform-types --experimental-test-isolation=none --test tests/mission-benchmark.test.ts
node --experimental-transform-types scripts/benchmark-missions.ts output/mission-benchmark 3
node --experimental-transform-types scripts/benchmark-missions.ts --verify output/mission-benchmark/report.json
```

Запуск локальный, без сети, GPU, настоящих БВС и поднятого веб-сервера. Результаты генерируются только внутри `output/mission-benchmark`. Проверка `--verify` возвращает ненулевой код при подмене/несогласованности. Она повторно проверяет:

1. Полноту заранее объявленного набора, наличие каждого повтора и обеих целей, включая отказные случаи.
2. Хеши входа, кандидата и соответствие текущим исходникам; изменение исходников во время прогона делает отчёт недействительным для этого релиза.
3. Ограничения маршрутов, неизменность заданий и ресурсов, последовательность базового плана, заявленные метрики.
4. Арифметику сравнений и итоговой статистики, привязку каждого положительного пакета доказательств к своему кандидату и входу.

Время CPU задним числом не восстанавливается: для проверки скорости следует повторить весь запуск. Число тестов и правильная арифметика не подтверждают официальный балл жюри.

Главные файлы: [report.json](../../output/mission-benchmark/report.json), [verification.json](../../output/mission-benchmark/verification.json). Рядом — `.mission.json`, оба `.candidate.json` для каждого критерия/повтора, `.evidence.json` только для подтверждённых полных планов. `unknown` остаются явно перечисленными. Каталог результатов не включается в Git автоматически; для сдачи нужно передать выбранный отчёт вместе с его файлами либо дать эксперту команды повторного запуска.

## Измеренный срез

Итоговый прогон проверен 20.09.2026 в 16:00:07 UTC: Node 24.14.1, Windows x64, AMD Ryzen 5 7430U, 12 логических потоков. 15 задач × 3 повтора. Семь задач дали полные допустимые планы обеих сторон; восемь остались отказными/неполными. В 45 повторах каждого критерия — 21 сопоставимая пара и 24 исключённые из процентов. Это не «21 независимая миссия». `--verify`: `passes-declared-model`, ошибок повторной проверки нет; все `unknown` сохранены.

Повторный прогон обновляет привязку к текущему составу исходников после добавления `mission-presentation.ts`: объединение одинаковых карточек и сводка проверок не изменяют решатель. Изменение времени относительно прошлого среза не трактуется как ускорение или замедление алгоритма; на машине параллельно выполнялась работа над интерфейсом.

| Показатель на сопоставимых парах | Результат среза |
|---|---|
| Медианное сокращение времени завершения | 5,82% |
| Медианное сокращение суммарного налёта | 0% |
| Максимум сокращения времени в отдельном примере | 58,88% — `mixed-fleet` |
| Максимум сокращения налёта в отдельном примере | 23,98% — `automatic-tradeoff` |
| Время вызова нашего решателя, обе цели | p50 39,78 мс; p95 109,10 мс; максимум 121,89 мс |
| Время вызова последовательного метода, обе цели | p50 15,45 мс; p95 44,00 мс; максимум 71,83 мс |
| Незавершённые нагрузочные задачи | 10 км² — `partial`; 100 км² — `not_found` |

В сетке параметров ни один из четырёх изменённых входов не дал полного результата: `parameter-grid-1`, `2`, `4` — `not_found`, `3` — `partial`. В частности, 1 м/с с направления 0° при полном заряде не приводит к найденному полному плану автоподбора; это **не доказательство невозможности такой миссии**. Трасса фиксирует неназначенные полосы и ограниченный поиск. Данный срез выявляет необходимость улучшения поиска, а не основание объявлять стенд готовым для любых условий.

Хеш итогового отчёта: `512da391d14e5396067240b4c4acbbefe50e8b30c8f1af0331dd1c7a1b24608c`. Числа производительности — наблюдения на этой машине, не SLA. Изменение фоновой нагрузки меняет длительность прогона; это само по себе не ускорение алгоритма между версиями.

Формулировка для защиты: **«На фиксированном опубликованном наборе мы измеряем результат против того же безопасного последовательного расчёта; показываем и выигрыш, и отсутствие выигрыша, и неудачи. Любой положительный маршрут можно перепроверить из экспортного пакета».** Не заменять это фразой «всегда быстрее на 59%».

После изменения ядра, схемы или проверок нужно снова выполнить команды и сверить цифры. Текущий машиночитаемый отчёт важнее исторического среза в этом документе.
