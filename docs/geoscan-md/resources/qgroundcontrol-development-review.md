## Архитектура и расширение

| Возможность | Суть | Решение для нашей команды |
| --- | --- | --- |
| FirmwarePlugin | Различия автопилотов, команд, параметров и поведения | Поддержку проверять по конкретной прошивке и типу БВС, не по наличию слова MAVLink |
| AutoPilotPlugin | Настройка компонентов аппарата | Не переписывать калибровки и подготовку реального БВС в хакатонном вебе |
| QGCCorePlugin, custom build | Изменение страниц, настроек, брендинга | Не делать полноценный форк GCS ради MVP: отдельный веб-планировщик и ограниченный адаптер дешевле в сопровождении |
| Fact System | Значения, типы, единицы, диапазоны и метаданные | Перенять принцип: одни и те же проверяемые параметры питают расчёт, форму и отчёт |
| QML/Qt controls, palette | Адаптивные панели и единый визуальный язык | Карта, тревоги, выбранный аппарат и режим должны читаться без опоры только на цвет |
| MockLink | Имитация соединения/параметров/миссий и ошибок | Использовать как образец тестов интерфейса; MockLink не моделирует полёт |
| Unit tests, CI, Docker build | Воспроизводимая сборка и автоматические проверки | Закреплять версии зависимостей и образов. Docker сборки QGC не равен готовому Docker-стенду нашей системы |

Источники: [developer guide](https://docs.qgroundcontrol.com/Stable_V5.1/en/qgc-dev-guide/), сохранённые статьи разделов customization, Fact System, architecture, getting started, testing.

## Формат `.plan`: риски конвертации

Документация описывает JSON с миссией, геозонами и rally points. Внутри сохраняются тип БВС, прошивка, домашняя точка, высоты, скорости, простые команды и составные элементы съёмки. [Описание Plan](https://docs.qgroundcontrol.com/Stable_V5.1/en/qgc-dev-guide/file_formats/plan.html).

Наши правила адаптера:

1. Не смешивать порядок координат: GeoJSON использует `lon, lat`; массивы QGC, показанные в документации, — `lat, lon`.
2. Хранить вертикальную систему отсчёта отдельно от числа высоты. Поле интерфейса `AltitudeMode` не считать автоматически равным MAVLink `frame`.
3. Не заменять `null` на ноль: в параметрах команд он может означать NaN/значение по умолчанию.
4. Не путать `doJumpId`, индекс JSON-массива и фактическую последовательность команд.
5. Составной Survey после развёртывания даёт больше команд, чем видно элементов в интерфейсе. Ограничение размера проверяется на выходной миссии.
6. После импорта и обратного экспорта сравнивать смысл, единицы, фазы камеры и маршрута. Побайтовое равенство не требуется, потеря смысла запрещена.

## Несогласованности, обнаруженные в документации

| Место | Что обнаружено | Что делать перед реализацией |
| --- | --- | --- |
| Plan JSON | Версии Survey/CorridorScan и геополигонов в примерах не везде совпадают с пояснениями | Получить реальные `.plan` из выбранной сборки; закрепить fixtures и тесты round-trip |
| Поле `inclusion` | Описание «включено/выключено» противоречит пользовательскому смыслу «зона включения/исключения» | Проверить исходный код выбранного commit и пример исключающей зоны. Не копировать это пояснение как контракт |
| Версии Qt | Страница сборки требует 6.11.1, история изменений содержит 6.10.1 | Авторитет для сборки — конфигурация выбранного commit, а не смешение страниц разных эпох |
| TLOG | Старый пример описывает устаревший пакет/размер и сырую запись памяти | Не реализовывать новый writer по этому примеру; применять совместимый парсер и реальные логи выбранного стека |
| Настройки custom build | Несколько файлов переопределяют значения в порядке загрузки | Сохранять все override-файлы, не только финальный JSON параметров |

Это выявленные расхождения текстов, а не подтверждённые баги программы. Исходный код перечисленных механизмов в этом проходе не тестировался.

## Полезное для оптимизации

В формате Survey уже есть `flyAlternateTransects`: порядок через один проход полезен самолёту при большом радиусе разворота. Не заявлять это нашей уникальной разработкой. Наш вклад должен быть в выборе порядка, распределении по разнородным БВС и измеримом результате на ограничениях заказчика.
