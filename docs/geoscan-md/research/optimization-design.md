# Алгоритмический план: Геоскан, ЛЦТ‑2026

Дата проверки: 15.09.2026. Приоритет — полный текст `5. Геоскан.pdf`, извлечение `tz-extracted.txt`, страницы 2–3 PDF. Это предлагаемый план реализации, не утверждённые организатором дополнительные требования. Команда: 2 человека. Гарантировать 1-е место нельзя; можно системно убрать причины проигрыша и доказать качество решения.

## 1. Что в ТЗ критично и что нельзя перепутать

- Название: **«Сервис планирования и распределения беспилотных авиационных работ»**.
- Два обязательных критерия: **время выполнения работ** и **суммарный налёт**. Налёт — рабочая трактовка в единицах времени в воздухе, НЕ износ оборудования и НЕ километраж. Единицы и начало/конец отсчёта подтвердить у экспертов.
- Рабочее определение makespan: от общего момента доступности флота до завершения последней посадки. Дополнительно показывать момент окончания последнего съёмочного участка, чтобы эксперты видели обе трактовки. Не смешивать эти показатели.
- Вход: произвольные стартовые/посадочные пункты, конкретные БВС с зарядом, AOI, вид съёмки, разрешённое пространство, NFZ, резервные площадки, скорость ветра. Направление ветра ТЗ прямо не перечисляет: добавить как опциональный параметр, не придумывать его молча.
- Миссия должна содержать не только линии галсов: старт → взлёт/набор → транзит → съёмка/переходы → возврат/снижение → посадка. Высота, скорость, ключевые точки, последовательность этапов и экспорт обязательны.
- В ТЗ указаны **201, 801, Gemini**. Старый отчёт о 401/701 не должен подменять этот флот. Поддержка пяти типов съёмки не означает, что каждый из трёх БВС совместим с любым сенсором: нужна таблица совместимости и явный отказ при несовместимости.

## 2. Рекомендуемая техническая ставка

**Проверяемый геометрический планировщик с учётом разных БВС и ветра; быстрый поиск допустимого решения; локальная оптимизация; независимый валидатор; сравнение с простым baseline.** ML необязателен по ТЗ. Не тратить критический путь двух человек на обучение сегментации, собственный автопилот, 3D-симулятор, цифровой двойник или интеграцию недокументированного API Geoscan Planner.

Минимальный стек: Python + FastAPI + Shapely + pyproj + NumPy; React/TypeScript + Leaflet/OpenLayers; сценарии и результаты в JSON. БД, очереди, Kubernetes и распределённые вычисления не нужны для первого работающего вертикального среза. CP-SAT — сменный backend оптимизации, а не обязательное условие первого демо.

Контур:

`InputValidator → CRS/Geometry → PayloadCoverage → FeasibleRouteCandidates → Assignment/LocalSearch → Schedule → IndependentValidator → KML/GeoJSON + Metrics`.

Каждый результат хранит `scenario_hash`, версию профилей, версию алгоритма, seed, настройки, тип модели ветра, флаг калибровки энергетики и список предупреждений. Это позволяет воспроизвести демо и ответить на вопрос «почему получилось именно так?».

## 3. Геометрия: реализуемая последовательность

1. **Валидация входа.** Пустые/самопересекающиеся полигоны, дубли, перепутанные lat/lon, неправильные единицы, отрицательный заряд, конфликт высот. Shapely `make_valid` может вернуть GeometryCollection, а не Polygon: тип и площадь после ремонта проверяются, существенное изменение требует подтверждения, не скрытого исправления. [S5]
2. **Метрическая CRS.** Хранить/экспортировать WGS84 lon,lat; считать площади, буферы, длины и дуги в подходящей локальной метрической проекции. `always_xy=True` исключает неявную перестановку осей. Для первой версии ограничить размер области/географический диапазон и сообщать о выходе за проверенную область применения, не считать метры в EPSG:4326. [S6]
3. **Развести съёмочную область и воздушное пространство.** `AOI` — то, что надо снять; `A_safe` — где может находиться аппарат. Обычно `A_safe = erode(A_permitted, margin) \ union(buffer(NFZ, margin))`. Маршрут может находиться за границей AOI, если это разрешённое пространство; нельзя автоматически запрещать все такие развороты. Если часть AOI недоступна, показать её отдельно и не уменьшать исходное задание молча. NFZ нельзя самостоятельно считать запретом фотографирования: это отдельная семантика, которую надо уточнить.
4. **Разбиение на связные рабочие участки.** Начать с polygon clipping и трапецеидального/полосового разбиения вдоль нескольких направлений; не нужен нейросетевой сегментатор. Сохранять holes и MultiPolygon. У мелких фрагментов явный порог: либо обслуживаем, либо отображаем необслуживаемый остаток, но не теряем его при округлении.
5. **Галсы под конкретную нагрузку.** Генерировать несколько углов: основные направления границы/минимального ориентированного прямоугольника, направление ветра и перпендикуляр к нему. Для каждого — оба направления входа и разные позиции первого галса. Число кандидатов ограничено и отображается в настройках эксперимента. Выбирать не минимальное число галсов, а лучшую оценку полного полёта с транзитами, разворотами и ветром.
6. **Связки и транзиты.** Для мультикоптера: граф видимости по вершинам расширенных препятствий или A* по сетке → сглаживание только после повторной проверки коллизий. Для самолётного профиля: криволинейные связки с минимальным радиусом/ориентацией; нельзя соединить галсы острым углом. Начать с проверенных Dubins-кандидатов; если нет допустимого варианта, пробовать другой порядок/угол или честно отвергать вариант. Не выдавать прямолинейный «объезд» за кинематически допустимый маршрут самолёта. Fields2Cover показывает готовое разбиение CPP на галсы, порядок и путь; его наземная модель не является готовой моделью авиации. [S3, S4]
7. **Проверять весь след.** В NFZ/за разрешённую границу не могут попадать транзит, дуги, набор/снижение, заход на посадку и аварийный маршрут, а не только рабочие галсы. Для дуг учитывать погрешность аппроксимации: буфер безопасности должен включать максимальное отклонение дуги от полилинии.

**Критическая оговорка:** Dubins в плоскости — геометрическая аппроксимация. Ветровой снос и ограничения воздушной скорости меняют фактическую кинематику. Радиус/скорость/ветровой диапазон должны исходить из документированного профиля или быть явно помечены как модельные параметры, требующие валидации. Нельзя обещать полётную безопасность по одной линии на карте.

## 4. Съёмка: качество задаёт допустимые маршруты

| Режим | Параметры, нужные планировщику | Что проверять |
|---|---|---|
| RGB | матрица, фокус, размер пикселя, GSD или высота, продольное/поперечное перекрытие, допустимая частота съёмки | шаг галсов, шаг триггера, скорость, покрытие края и швов |
| Мультиспектральная | геометрия каналов/общего footprint, требуемое перекрытие, частота, профиль камеры | использовать ограничивающий канал/общую гарантированную область, не ширину RGB по умолчанию |
| ИК | геометрия ИК-сенсора, GSD, частота, допустимая скорость/экспозиция | собственный footprint и ограничения качества; нельзя просто изменить подпись RGB |
| LiDAR | эффективная ширина полосы/FOV, высота, частота импульсов/сканирования, требуемая плотность и перекрытие | связь скорости с плотностью; паспортные параметры, а не придуманный универсальный коэффициент |
| Геофизическая | межпрофильное расстояние, высота, скорость, требования прямолинейности и стабилизации, контрольные линии — если заданы | время стабилизации после поворота, допустимость аппарата/подвеса; не сводить к фотокамере |

Для плоской местности и надирной pinhole-модели: `W = H × sensor_width / focal_length`; шаг галсов `d = W × (1 − sidelap)`; `GSD = H × pixel_pitch / focal_length`; шаг фототриггера определяется продольным footprint и frontlap. Единицы должны совпадать. Это модельная геометрия, не эмпирическая гарантия качества изображения. QGC прямо предупреждает, что перепад рельефа меняет фактическое перекрытие и может создавать риск столкновения. [S7]

Нет паспортных данных по отдельному сенсору → пользователь вводит проверенный профиль; интерфейс не ставит ложную галочку «режим поддержан». Нет DEM → явно плоская модель, обозначенная высотная система и предупреждение; полноценное terrain following не входит в обязательный первый срез.

**Как совместить разную ширину съёмки и распределение:** делить задание на общие геометрические участки, но строить галсы участка отдельно для каждого совместимого БВС/сенсора. Не раздавать всем один RGB-grid и не сравнивать их по числу одинаковых полос. При объединении соседних участков перестраивать их общий маршрут — иначе потери на межучастковые развороты будут искусственно завышены. Для границ участков сохранять требуемое перекрытие и учитывать повторную съёмку в затратах.

## 5. Ветер: направленная стоимость, а не коэффициент ко всему полёту

Для прямого участка направления `u` и постоянного горизонтального ветра `w`: `w_parallel = w·u`, `w_perp = w − w_parallel·u`. При заданной воздушной скорости `Va` и удержании наземного курса:

`Vg = w_parallel + sqrt(Va² − |w_perp|²)`; `t = L / Vg`.

Это вывод из векторного равенства воздушной и путевой скоростей, а не паспортная модель конкретного БВС. Применимо, если `|w_perp| < Va`, `Vg > 0`, выбранная Va находится в допустимом диапазоне и режим разрешён паспортными ограничениями ветра. Проверять ограничение бокового ветра отдельно, если оно есть. Для съёмки дополнительно действует верхняя путевая скорость сенсора.

- `cost(A→B) != cost(B→A)`. Переворот направления обхода может изменить и рабочее время, и возможность возвращения.
- Проверка `ветер < паспортного максимума` не заменяет расчёт пути и батареи.
- Есть только модуль ветра без направления → либо требовать направление для направленной модели, либо включить явно маркированную консервативную оценку с худшим встречным ветром. Нельзя молча выбрать северный ветер.
- В первой версии — один постоянный вектор на сценарий, паспортные ограничения и консервативный запас. Пространственно-временные поля/порывы — следующий этап; в демо можно выполнить sensitivity analysis по нескольким сценариям ветра, не выдавая его за прогноз.
- Не применять формулу прямого участка к повороту одним средним курсом: разбить дугу на достаточно короткие сегменты и проверить ограничения скорости/кинематики; погрешность и предел модели документировать.

## 6. Заряд, посадка и резерв: условия допустимости, не штраф

**Базовый инвариант:** для каждого вылета хватает ресурса на взлёт, набор, транзиты, съёмку, развороты, возврат/снижение, посадку и заданный запас. Допустимость не «покупается» улучшением целевой функции.

Предпочтительная модель при наличии данных: `E_route = Σ(P_phase(Va, payload, ...) × t_phase) + E_takeoff/landing`, с корректным учётом отсутствия двойного счёта фаз. Условие: `E_route + E_reserve <= E_available(SoC, battery_state)`.

Если есть лишь рекламное «до N минут», **не утверждать**, что `N × SoC` — точная доступная продолжительность. В MVP использовать редактируемый консервативный временной бюджет для данного заряда/нагрузки, с названием «расчётная модель, не калибрована по логам». Источник коэффициентов/бюджета показывать. Не выдумывать одинаковое время зарядки для 201/801/Gemini.

Резервная площадка — не ближайшая точка по прямой. Нужны: тип БВС/способ посадки, геометрия зоны захода/посадки, разрешённый путь, ветер, доступность и ресурс достижения. Произвольность координат в ТЗ не означает физическую пригодность любого места.

Для каждого контрольного состояния `q` полёта:

`E_used(q) + min_{r in suitable_reserves(q)} E_diversion(q,r) + E_land(r) + margin <= E_available`.

Если множество пусто, вариант недопустим в режиме, требующем постоянной достижимости резерва. Само требование «резерв доступен из каждой точки» — предлагаемая строгая политика, уточнить у экспертов; наличие входного слоя площадок не определяет эту семантику автоматически.

В MVP проверить состояния в начале/конце фаз, на поворотах и с ограниченным шагом. Это **дискретная проверка**, не непрерывная гарантия. Для сертификата на весь сегмент нужна консервативная верхняя оценка расхода/обхода на промежутке или адаптивное дробление с доказанным запасом. Не писать «безопасно из любой точки» при простой выборке нескольких waypoint.

## 7. Распределение и несколько вылетов

### P0: жадный конструктивный алгоритм + локальные улучшения

1. Для участка и совместимого БВС получить реальные допустимые маршруты с разными углами/входами/выходами и посадочными пунктами; сохранить расходы, время, геометрию и причины отбраковки.
2. Сначала назначать трудные участки: мало совместимых аппаратов, мало энергетического запаса, изолированная геометрия. Это уменьшает риск «потратить единственный подходящий аппарат на простую работу».
3. В режиме времени выбирать допустимую вставку с минимальным новым makespan; в режиме налёта — с минимальным приращением полного воздушного времени. Порядок участков не фиксировать навсегда.
4. Пробовать перенос пограничного участка, обмен двух участков, смену порядка/направления, объединение соседних участков, изменение точки посадки. После изменения перестраивать затронутые маршруты и повторять hard checks.
5. Хранить лучший допустимый incumbent. При timeout вернуть его, а не пустой экран. Если допустимого варианта нет, объяснить конкретные причины. Отсутствие решения у эвристики не является доказательством отсутствия решения задачи.

### P1: несколько вылетов с ограниченной логистикой

Начать с повторных вылетов **с одной базы**, с заданным числом заряженных батарей и фиксированным подтверждённым временем обслуживания/замены. Не обещать мгновенный reset SoC. Каждый аппарат выполняет не более одного вылета одновременно. Суммарный налёт не включает наземное обслуживание, makespan включает ожидание и обслуживание между вылетами.

Если первая посадка отличается от следующего старта, требуется объяснимая связь: следующий вылет стартует там же либо задано наземное перемещение с длительностью/ресурсом. Нельзя телепортировать БВС обратно. Полная оптимизация обмена батарей между базами, нелинейной зарядки и наземных экипажей — P2.

Межаппаратные конфликты: минимально показать временные интервалы и детектировать пересечения траекторий по пространству и времени; выдавать предупреждение/разводить старты в определённой модельной политике. Простое пересечение линий на 2D-карте не равно столкновению; одинаковая высота с одновременным пересечением — не «безопасный план». Полный 4D deconfliction не заявлять без отдельной реализации.

## 8. CP-SAT: где оправдан, какие переменные

CP-SAT полезен после работающей геометрии для выбора **заранее проверенных** вариантов и расписания; не заставлять его одновременно открывать всю непрерывную геометрию. Библиотека поддерживает целочисленные ограничения, интервалы и ограничения отсутствия перекрытия. [S1, S2]

Практичная restricted-master модель:

- `j` — общий участок/задание; `r` — кандидат целого вылета с фиксированным БВС `i(r)`, стартом, посадкой, маршрутом, сенсором, длительностью `t_r` и множеством обслуживаемых участков `J_r`;
- `z_r ∈ {0,1}` — выбрать кандидат;
- `Σ_{r: j∈J_r} z_r = 1` для каждого обязательного участка. Геометрическое перекрытие на швах допустимо; равенство касается ответственности за участок, не запрета перекрытия изображений;
- optional interval `[s_r, e_r]` длительности `t_r`; `NoOverlap` для одного БВС. Операции обслуживания/батареи/посадочной инфраструктуры — отдельные интервалы/ресурсные ограничения при включённом режиме;
- энергия и геометрия кандидата уже проверены, но порядок применения батарей и непрерывность местоположения должны сохраняться в расписании; один `NoOverlap` этого не обеспечивает;
- `Cmax >= e_r` только для выбранных кандидатов; `min Cmax` или `min Σ t_r z_r`.

Для первой CP-SAT версии разумно ограничить один вылет на БВС: `Σ_{r:i(r)=i} z_r <= 1`. Многовылетная версия требует дополнительных условий логистики, а не удаления этого ограничения одной строкой.

Время/энергию масштабировать в целые единицы, документировать точность; для hard-лимитов консервативно округлять расходы вверх и доступные бюджеты вниз. Слишком грубое округление может отбросить допустимые решения, слишком мелкое увеличивает численные диапазоны. После оптимизации независимый валидатор проверяет результат в исходных единицах.

`OPTIMAL` означает оптимум **этой дискретной модели и её каталога кандидатов**, а не всех возможных непрерывных траекторий. `FEASIBLE` — найден допустимый вариант, оптимальность не доказана. `UNKNOWN` — поиск не дал заключения; `INFEASIBLE` — доказана недопустимость только выбранной модели. [S1]

## 9. Целевые функции, нижние оценки и честные цифры

Для выбранных вылетов:

`F_time = max_r(end_landing_r) − common_start`;

`F_airtime = Σ_r(landing_r − takeoff_r)`.

Рабочие галсы, транзиты, ожидание в воздухе, дуги, набор/снижение входят в налёт; зарядка и ожидание на земле — нет. Время съёмки отдельно показать в разложении. Расстояние — диагностическая метрика, но не подмена налёта.

Сначала два независимых режима с теми же входными данными. Вторичный критерий разрешает ничьи: при одинаковом makespan выбрать меньший налёт и наоборот. Взвешенную сумму без нормировки не использовать вместо двух заявленных критериев.

Нижние оценки:

- `solver.best_objective_bound` — подтверждённая нижняя граница для минимизации в конкретной CP-SAT модели. Gap `(incumbent − lower_bound) / max(abs(incumbent), ε)` с явным указанием модели; не публиковать при отсутствии допустимого incumbent. [S8]
- Простая физическая проверка: для одной модальности при доказанной верхней границе производительности `q_i` в м²/с: `T_makespan >= area / Σ_i q_i`, `T_airtime >= area / max_i q_i`. Игнорируются перелёты/повороты/зарядки — это оптимистичные, часто слабые оценки. Если качество/высота/сенсоры делают `q_i` не верхней границей, формула перестаёт быть доказательной. Для совместной съёмки несколькими модальностями нельзя механически складывать границы и двойным счётом завышать их.
- Для маленьких фиксированных наборов участков проверить перебором все назначения/порядки в той же ограниченной модели. Сравнение помогает найти баги и оценить качество эвристики, но не доказывает непрерывный глобальный оптимум.

Честная формулировка на защите: «На N опубликованных сценариях наш метод даёт такой-то выигрыш относительно конкретного baseline при одинаковых ограничениях; M решений проверены точным решателем для фиксированной модели; показатели воспроизводимы». Пока тесты не выполнены, любые проценты выигрыша — **целевые гипотезы, не результаты**.

## 10. Независимый валидатор и обязательные тесты

Валидатор — отдельный модуль, не функция, возвращающая флаг из самого оптимизатора. Он читает экспортированную миссию и исходный сценарий, заново вычисляет нарушения.

Проверки: маршруты целиком внутри разрешённого пространства; нет пересечений с NFZ с учётом буферов; приемлемая кинематика; полный список фаз; заряд; совместимость сенсора; покрытие/перекрытия; допустимые старт/посадка; резерв; непрерывность времени/местоположения; нет дубликатов/потерь задач; корректные единицы и высотные системы.

Минимальная батарея сценариев:

1. Прямоугольник, штиль, одинаковые аппараты: ручная проверка симметрии.
2. Вогнутый AOI с отверстием/NFZ: проверка транзитов и разворотов, а не только галсов.
3. Два удалённых полигона, произвольные базы: цена транзита и выбор посадки.
4. Смешанные 201/801/Gemini и разные остатки заряда: гетерогенность реально меняет назначение.
5. Ветер в противоположных направлениях: асимметрия стоимости и возврат.
6. Пограничный ресурс: небольшое увеличение работы/ветра делает вылет недопустимым, система объясняет почему.
7. Недостижимая резервная площадка; несовместимый тип посадки.
8. AOI частично вне достижимого/разрешённого пространства: исходная площадь не исчезает из отчёта.
9. Сравнение режимов: меньше makespan при большем общем налёте — допустимый и понятный trade-off.
10. Отдельный профиль каждого из пяти видов съёмки; неподдерживаемая связка сенсор/БВС явно отвергается.
11. Несколько вылетов: запас батарей, обслуживание и старт следующего вылета соответствуют реальности.
12. Импорт KML/GeoJSON обратно и пересчёт; не только проверка, что скачался файл.

Baselines: равная площадь на БВС (с тем же валидатором); ближайшая база/жадное назначение; наш метод без ветровой стоимости для ablation; маленький перебор/CP-SAT как контроль. Нельзя сравнивать безопасный полный маршрут с baseline, который просто исключил возврат и поэтому искусственно «быстрее».

Таблица бенчмарка: сценарий, размер/число вершин/БВС/галсов, hardware, seed, solve-time, makespan, общий налёт, доля покрытой исходной AOI, нарушения, статус/граница/gap при наличии. Бюджеты времени поиска 1/5/15 секунд можно исследовать; не обещать их как доказанную производительность до измерений.

## 11. Экспорт: незаметная ошибка, которая может испортить защиту

Внутренний формат миссии должен быть единственным источником KML и GeoJSON. Для каждого этапа: `mission_id`, `uav_id`, `sortie_id`, `sequence`, `phase`, `speed_mps`, `speed_reference`, `altitude_m`, `altitude_reference`, `start_site_id`, `landing_site_id`, `sensor_mode`, время/оценка ресурса. В KML — Folder/Placemark/ExtendedData; в GeoJSON — отдельные Feature с properties, а не одна безымянная LineString.

GeoJSON RFC 7946 задаёт lon,lat и при наличии третьей координаты — высоту над эллипсоидом WGS84. **Нельзя записывать туда AGL 100 м и считать это стандартной высотой.** Если геодезическое преобразование высоты отсутствует, хранить 2D-геометрию и явные `altitude_m` + `altitude_reference` в свойствах. KML различает `relativeToGround` и `absolute`; не переносить числовую высоту между форматами без её семантики. [S9, S10]

KML/GeoJSON по ТЗ — обменный результат. Сам по себе такой файл не является доказательством готовой команды автопилоту/совместимости с Planner. Показывать round-trip и карту; аппаратную интеграцию заявлять только после реальной проверки.

## 12. Реалистичный порядок для двух человек

Оценки ниже — диапазоны для планирования, не объявленные сроки хакатона и не гарантия трудозатрат. Один рабочий день считать по реально доступным продуктивным часам команды.

| Этап | Человек A: геометрия/алгоритмы | Человек B: UI/API/QA | Оценка на команду | Критерий выхода |
|---|---|---|---|---|
| 0. Контракт данных | точные метрики, модели профилей, 3 ручных сценария | схема API, мастер ввода, макет карты | 6–10 человеко-часов | один сохранённый валидный сценарий, список открытых вопросов |
| 1. Вертикальный срез | одна простая область, галсы, обе цели, один вылет | карта, фазы, импорт/экспорт, API | 16–24 ч | end-to-end без моковых метрик |
| 2. Обязательная специфика | NFZ/транзиты/развороты, направленный ветер, заряд/резерв, совместимость нагрузок | редакторы слоёв/профилей, ошибки, сравнительный экран, валидатор экспорта | 24–36 ч | сложный смешанный сценарий, осмысленный отказ на невозможном |
| 3. Доказательство качества | baseline, локальный поиск, маленький перебор | бенчмарк, тесты, документация, репетиция | 16–24 ч | воспроизводимые цифры и весь сдаваемый комплект |
| P1. Только после P0 | CP-SAT и/или повторные вылеты; выбрать по остатку времени | расписание, профиль батарей, стресс-тесты | ещё 16–32 ч | измеримый выигрыш или закрытый важный пробел |

Итого обязательный вертикальный план: ориентировочно **62–94 человеко-часа**, а не «всё за вечер». Это оценка для двух опытных участников при отсутствии серьёзных проблем с исходными данными; интеграционные неизвестные могут увеличить её. Если доступно меньше, сначала уменьшать число алгоритмических улучшений и декоративный UI, **не** убирать обязательные поля ТЗ/экспорт/проверку ограничений. Точное покрытие всех режимов и физическая валидация зависят от полученных параметров полезных нагрузок.

Главное правило feature freeze: последние примерно 20–25% имеющегося времени — только исправления, воспроизводимость, документы и защита. Не начинать ML/3D/новый solver после начала этой фазы.

## 13. Основные риски и действия

| Риск | Почему опасен | Что делать |
|---|---|---|
| Оптимизировать износ вместо налёта | прямое несоответствие полному ТЗ | исправить метрики, формулы, экран сравнения и слайды |
| Маркетинговые характеристики вместо профилей полёта | неверная батарея/ветер/повороты | источник и статус каждого параметра; вопросы экспертам; консервативный режим |
| Неизвестный шаг/качество LiDAR и геофизики | «пять режимов» только в dropdown | схема режимов, реальные параметры; явная неподдерживаемость конкретной связки |
| Две модели задач для двух критериев | некорректное сравнение | один сценарий, одна геометрия/валидатор, меняется только objective |
| Ошибки обратного пути/резерва | красивый невыполнимый маршрут | направленные стоимости, строгие условия энергии и посадки |
| Одна линия между концами галсов | пересечение NFZ, невозможный поворот | кинематические связки и проверка полного следа |
| Выпиливание недоступной AOI | ложные 100% покрытия | знаменатель — исходное задание; отдельный слой невыполненной области |
| Restricted optimum выдан за глобальный | сильный вопрос экспертов рушит доверие | явно каталог кандидатов/статус/gap/границы модели |
| Перегрузить двух человек CP-SAT+ML+3D | нет законченного продукта | сначала P0, затем одно улучшение с наибольшей ценностью |
| Нет рельефа и авиационных данных | нельзя обещать реальную безопасность | прототип планирования, плоская модель, предупреждения, операторская проверка |
| Неправильная высота в экспорте | формально валидный, семантически опасный файл | altitude_reference; round-trip; отдельные свойства AGL |
| Недетерминированное демо | случайно плохой результат на сцене | сценарий/seed/версии; сохранённый честный прогон; локальная резервная демонстрация |

## 14. Что спросить у экспертов первым сообщением

1. Как измеряется «время выполнения работ»: до конца съёмки или последней посадки? Налёт — сумма времени в воздухе с взлётом/посадкой/ожиданием?
2. Будут ли конкретные камеры/нагрузки, GSD/перекрытия, LiDAR-плотность и параметры геофизики? Какие связки допустимы для 201/801/Gemini?
3. Предоставят ли min/max скорость, радиус/динамику поворота, ограничения взлёта/посадки, модели заряда/ветра и данные нагрузок? Что считается достаточной моделью ресурса?
4. Как интерпретировать разрешённое пространство: 2D/высотные эшелоны/временные окна? Обязательна ли достижимость резервной площадки из каждой точки маршрута?
5. Нужны ли несколько вылетов, смена батарей и переезд между базами? Какой лимит флота/AOI/времени расчёта будет на оценке?
6. Экспорт — общие KML/GeoJSON с атрибутами или есть конкретная схема импортёра? Нужен ли полётный импорт в Planner/QGC либо достаточно обменного файла?

## Проверенные первоисточники

Все ссылки проверялись 15.09.2026. Утверждения ниже — только то, что непосредственно поддерживает источник; предлагаемый алгоритм и оценки трудозатрат — наши инженерные выводы.

- **S1 — Google OR-Tools, CP-SAT Solver:** https://developers.google.com/optimization/cp/cp_solver — целочисленное моделирование и определения OPTIMAL/FEASIBLE/INFEASIBLE/UNKNOWN. Не является обещанием скорости на нашем наборе.
- **S2 — Google OR-Tools, Job Shop:** https://developers.google.com/optimization/scheduling/job_shop — интервальные переменные, предшествование, отсутствие перекрытия и makespan в примере расписания.
- **S3 — Fields2Cover, статья авторов:** https://arxiv.org/abs/2210.07838 — модульное построение покрытия: headland, swaths, route, path; исследование предназначено для наземных сельскохозяйственных машин, не готовая авиационная сертификация.
- **S4 — Fields2Cover, Path Planning:** https://fields2cover.github.io/source/tutorials/path_planning.html — минимальный радиус, Dubins и непрерывная кривизна; Reeds–Shepp допускает движение назад и не должен автоматически использоваться для самолётного профиля.
- **S5 — Shapely make_valid:** https://shapely.readthedocs.io/en/latest/reference/shapely.make_valid.html — исправление геометрии может изменить тип результата, включая GeometryCollection.
- **S6 — pyproj Transformer:** https://pyproj4.github.io/pyproj/dev/api/transformer.html — преобразование CRS и управление порядком осей `always_xy`; версию библиотеки проекта фиксировать отдельно, документация dev не означает, что проект должен использовать dev-релиз.
- **S7 — QGroundControl Survey:** https://docs.qgroundcontrol.com/master/en/qgc-user-guide/plan_view/pattern_survey.html — сетка по полигону, параметры камеры/перекрытия, развороты и предупреждения о рельефе.
- **S8 — исходная схема ответа OR-Tools:** https://github.com/google/or-tools/blob/stable/ortools/sat/cp_model.proto — `best_objective_bound` определён как доказанная нижняя граница для минимизации; interval/no_overlap/cumulative имеют формальную семантику.
- **S9 — RFC 7946, GeoJSON, §§3.1.1 и 4:** https://www.rfc-editor.org/info/rfc7946/ — порядок lon,lat; optional третья координата — метры относительно эллипсоида WGS84.
- **S10 — Google KML Altitude Modes:** https://developers.google.com/kml/documentation/altitudemode — `relativeToGround` означает высоту над землёй, `absolute` — относительно уровня моря.

Публичные страницы Geoscan 201/801/Gemini при прямом открытии в этой проверке возвращали Internal Error; их паспортные числа здесь намеренно не пересказывались. БВС и нагрузки должны уточняться по предоставленным материалам/доступным официальным руководствам. Ссылки из старого отчёта не подменяют фактический список ресурсов нового ТЗ.
