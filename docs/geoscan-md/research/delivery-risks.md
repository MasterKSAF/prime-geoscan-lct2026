# Геоскан: реализация, контроль качества и риски для двух человек

Проверено по извлеченному полному ТЗ, предметному разбору `geoscan-domain.md` и тексту шаблона презентации. Дата анализа — 15.09.2026. Это инженерный план, не новое требование организатора. Фактический срок сдачи, навыки команды, доступность экспертов и тестовых данных неизвестны. План ниже предполагает **12 рабочих дней × 2 человека × 6 часов = 144 человеко-часа**. Эти 12 дней не являются календарем хакатона.

## 1. Реалистичный вывод

Гарантировать первое место нельзя: неизвестны конкуренты, скрытые проверки, трактовки критериев и оценки экспертов. Управляемая цель — предоставить проверяемое соответствие ТЗ и доказательства качества, а не обещание победы.

Для двух опытных разработчиков за 144 часа реалистичен **узкий, воспроизводимый планировщик**, а не готовая авиационная система. Наиболее рискованные части: кинематически допустимый маршрут самолета 201, резервные площадки, энергия/ветер, отсутствие профилей LiDAR и геофизики. До подтверждения данных нельзя обещать полное физическое соответствие для всех трех моделей и пяти типов съемки.

Минимизация времени выполнения работ и минимизация суммарного налета — обязательные разные постановки из ТЗ. «Износ» и «километры» не заменяют второй критерий. Рабочая трактовка налета — суммарное время в воздухе; ее нужно подтвердить у экспертов. В режиме минимального времени работ учитывается конец последней миссии, а не сумма длительностей.

Два обязательных принципа:

- **Сначала допустимость, затем улучшение целевой функции.** Невалидный короткий маршрут не является выигрышем.
- **Пробелы видны пользователю.** «Не рассчитано», «не поддержано», «тайм-аут» и «невозможно при заданных ограничениях» — разные состояния. Отсутствие результата эвристики не доказывает невозможность решения.

## 2. Архитектура без лишней инфраструктуры

Рекомендуемая для этой команды архитектура — модульный монолит: **Python + FastAPI; React + TypeScript + OpenLayers; JSON-файлы сценариев и SQLite для заданий/результатов**. Это выбор команды, не требование ТЗ. PostgreSQL/PostGIS в ТЗ необязательны. Не закладывать обязательные Celery, Redis, Kubernetes, микросервисы, учетные записи, биллинг, свою тайловую платформу и управление реальными БВС.

| Модуль | Ответственность | Выходной контракт | Владелец |
|---|---|---|---|
| `schemas / scenario` | Координаты, зоны, площадки, парк, сенсоры, ветер, единицы, исходные допущения; версия схемы | Нормализованный сценарий + ошибки валидации; неизменяемый оригинал | B, ревью A |
| `profiles` | Отдельный экземпляр БВС, камера, заряд, источник параметров, версия, неизвестные величины | Проверяемые возможности и ограничения конкретного аппарата | B, предметное ревью A |
| `geometry / coverage` | Метрическая проекция, полигоны с отверстиями, разбиение работы, footprint, съемочные линии | Покрываемые участки с параметрами сенсора; отдельно непокрытая область | A |
| `trajectory / cost` | Подлет, съемка, развороты, возврат, взлет/посадка; ветер и бюджет | Направленно-зависимые стоимости и допустимые траектории; причины отказа | A |
| `allocation / schedule` | Выбор аппарата, распределение, два критерия, разрешенные задержки запуска | Лучшее найденное расписание; метод, статус, время расчета, seed | A |
| `validator` | Повторная независимая проверка результата: зоны, покрытие, совместимость, бюджет, запасные площадки, конфликты | Список проверок `pass / fail / not_checked`; детализация нарушения | A; B ведет черные тесты |
| `export` | Индивидуальные GeoJSON/KML, маршруты и точки, высоты, скорость, старт/посадка, этапы | Архив заданий + manifest; обратное чтение; потери полей явно указаны | B |
| `web / report` | Редактирование карты, каталог, сравнение критериев, временная шкала, причины отказа | Один согласованный результат без расхождения карты, таблицы и экспорта | B |
| `fixtures / benchmark` | Зафиксированные сценарии, одинаковые ограничения baseline и решения, журнал измерений | Воспроизводимый отчет, исходные сценарии, параметры машины и версии | Оба |

Практические ограничения реализации:

- Конвертировать входной GeoJSON `[долгота, широта]` в подходящую локальную метрическую систему для расчета; отображать обратно в географических координатах. Проверять выбранную область допустимости проекции. Не считать расстояния в градусах или в экранных пикселях.
- Высоту хранить явно: значение, единица, система отсчета (`AGL / AMSL / относительно старта`). Нельзя без преобразования переносить одно значение между этими режимами.
- Геометрия съемки и траектория воздушного судна — разные сущности. Полоса камеры может пересекать границу ROI, но траектория, развороты и подлет должны удовлетворять ограничениям воздушного пространства.
- Одна фоновая вычислительная задача на локальном демонстрационном сервере; жесткий лимит времени и размера входа, детерминированный seed, отмена. Вычисление не блокирует HTTP-обработчик. Если нужен отдельный процесс Python, проверить запуск на Windows; не вводить внешнюю очередь ради одного пользователя.
- В SQLite хранить статус, версии, входной JSON, ссылки на результаты. Геоиндекс и многопользовательская конкурентная запись не нужны для P0. Не выдавать такую конфигурацию за production-развертывание для сотен операторов.
- Минимальный API: создание расчета; получение статуса/результата; отмена; экспорт. Точный набор ручек — проектное решение. Автодокументация API не заменяет инструкции запуска и известные ограничения.
- `result` включает `input_hash`, `schema_version`, `profile_versions`, `objective`, единицы метрик, `assumptions`, `validation`, `solver_status`, `seed`, время расчета. Это дешевле, чем затем объяснять невоспроизводимые цифры.
- Проверяющий модуль не должен просто доверять флагам генератора. Например, он повторно пересекает экспортированные траектории с зонами и заново суммирует этапы. Для малых задач использовать ручные ответы/перебор как отдельную проверку.

## 3. Честная граница P0

**В P0 нацелиться:** ввод всех сущностей ТЗ; реестр трех заданных моделей с источниками; модель всех пяти типов съемки; физически осмысленная геометрия для согласованных профилей; ограниченный размер задачи; два критерия; валидатор; индивидуальный экспорт; воспроизводимые сценарии и защита.

**Условия, которые нельзя скрывать:**

1. Пять пунктов в выпадающем списке не равны поддержке пяти типов съемки. Для LiDAR и геофизики нужны подтвержденные совместимые профили либо отдельно согласованные пользовательские параметры и положительные тесты. Отказ «нет совместимого сенсора» — правильное поведение, но не закрытая функциональность.
2. Точки старта и резервной посадки сами по себе не подтверждают пригодность площадки для конкретного БВС. При отсутствии геометрии/условий это операторские допущения, отмеченные в отчете.
3. Фиксированный ветер и плоский рельеф могут быть допустимым ограничением исследовательского прототипа, но не дают оснований заявлять безопасность реального полета. Возможность такого сужения согласовать с экспертами.
4. «Один вылет на аппарат» — предлагаемое ограничение объема разработки, **не написано в ТЗ**. Если для оценки ожидаются повторные вылеты, их надо включить, сократив P1, а не выдавать недоделанное расписание за полное решение.
5. Геоскан 201 нельзя молча исключить из обязательного набора профилей: он дан в ресурсах. Если точные ограничения отсутствуют, отделить расчетный профиль с явными допущениями от подтвержденной производителем модели. Если маршрут с разворотами не проходит валидацию, не назначать на него самолет.

**P1 только после зеленого P0:** несколько вылетов и смена АКБ; DEM и terrain-following; подтвержденный импорт в конкретную версию Planner/QGC; локальное перепланирование; более сильная оптимизация. Сроки и обязательность многовылетности/рельефа уточняются, поэтому этот приоритет может измениться.

**Исключить из конкурсного ядра:** обучение сегментации без датасета; нейросеть ради демонстрации ML; распознавание препятствий без доказуемой точности; управление бортами; реальное разрешение полетов; авиационную сертификацию. CV-компетенция здесь полезна прежде всего для съемочной геометрии, GSD, перекрытия, частоты кадров и смаза.

## 4. План на 144 человеко-часа

Роли: **A — оптимизация/GIS/backend; B — интерфейс/контракты/экспорт/QA**. Это не оценка фактических навыков участников: неизвестны. При отсутствии у одного участника уверенного Python/GIS или у другого React/TypeScript сначала уменьшить объем и переоценить срок. В каждом шестичасовом блоке уже находятся короткая синхронизация, ревью и тесты; они не добавляются сверху.

| День | A — 6 часов | B — 6 часов | Проверяемый выход дня |
|---|---|---|---|
| 1 | Декомпозиция полного ТЗ, определения двух целей, перечень физических неизвестных, контракт расчета, ручной маленький пример | Каркас приложения, схема сценария, карта и поля всех входов, каталог документов/профилей | Один сохраненный сценарий проходит UI → API → JSON; отправлен единый список вопросов экспертам |
| 2 | Проекция, геометрия ROI/holes/allowed/no-fly, входные проверки; простые линии покрытия | Рисование/импорт зон и площадок, выбор парка и сенсоров; отображение ошибок с привязкой к объекту | Невалидный полигон и переставленные координаты не дают «успешный расчет»; метры проверены на ручном примере |
| 3 | Кинематическая модель коптера и 201: ненулевые развороты/подлет; выявление неподдержанных случаев | Полные профили трех моделей: источники, единицы, неизвестные параметры; карточка миссии | **G1:** траектория 201 на простой сцене проходит проверку разворотов либо зафиксирован критический блокер |
| 4 | Footprint/шаги для согласованных сенсоров; стоимость полета с ветром, взлетом/посадкой и бюджетом | Ввод ветра, заряда, высот; UI допущений; сценарии смены камеры/ветра/заряда | Одна миссия end-to-end: изменение параметра меняет расчет причинно, а не только надпись |
| 5 | Детерминированный ограниченный baseline и эвристика распределения по двум целям, ограничение времени | Переключение критерия, раскраска по БВС, таблица этапов и временная шкала; сохранение сравнений | Две цели вычисляются из одного состава работ и одинаковых ограничений; лучший baseline не теряется |
| 6 | Валидатор траекторий/покрытия/бюджета; перерасчет метрик; отказы и `no_solution_found` | Черные тесты API/UI; ранний GeoJSON; проверка соответствия карта ↔ данные | **G2:** валидный многобортный end-to-end и маленький проверяемый пример trade-off целей |
| 7 | Достижимость совместимой резервной площадки на заданной дискретизации; конфликты по времени и задержки вылета | Показ запасных путей, конфликтов и результатов проверок; случаи невозможного входа | Отказ при недостижимом резерве; конфликт не исчезает от простого изменения цвета/высоты |
| 8 | Исправление выявленных нарушений; сокращение перебора и безопасные ограничения размера задачи | GeoJSON/KML каждого БВС, все требуемые поля, manifest, обратное чтение и согласованная семантика высот | Экспорт возвращается в приложение без потери обязательной информации; некорректная миссия не маркируется готовой |
| 9 | Фиксированный набор корректных/некорректных сценариев; параметры тайм-аута и seed | Положительные/отрицательные сценарии пяти типов съемки, матрица соответствия, чистый запуск на втором ПК | **G3:** все обязательные ветки имеют доказательство либо явно открытый пробел; исходники запускаются вне машины автора |
| 10 | Измерения против baseline на неизменных сценах, малые точные проверки, прогон увеличения размера | Таблица измерений, воспроизводимые команды, документация пользователя/API/ограничений | **G4:** только реальные цифры; указан размер задачи/машина/версии/лимит времени; нет нарушений в принятых решениях |
| 11 | Сложные вопросы экспертов; проверка всех численных утверждений; ревью документации | Презентация по шаблону, обязательные блоки, сценарий защиты, запись резервного видео | Защита полностью проходит без интернета; слайды не обещают больше, чем демонстрирует код |
| 12 | Буфер 6 ч: только критические дефекты, проверка release-кандидата | Буфер 6 ч: упаковка, повторный запуск, проверка ссылок/экспорта/сдачи, репетиция | **G5:** финальный пакет и независимый запуск; новый функционал запрещен |

Итого: A — 72 часа, B — 72 часа. Из них день 12 — **12 часов общего резерва**, а не бесплатное время для нового функционала. План предельно плотный: если неопределенности снимаются поздно, объем надо уменьшать раньше, а не расходовать резерв на фундаментальную переработку.

## 5. Критический путь и правила stop/go

Критический путь: **трактовка задачи и профили → корректная геометрия/траектории → направленные стоимости → распределение → независимая проверка → экспорт → воспроизводимые измерения → защита**. Интерфейс идет параллельно на стабильном контракте. Его полировка не должна блокировать геометрию и валидатор.

| Ворота | GO | STOP / смена плана |
|---|---|---|
| G0 — конец дня 1 | Есть контракт, роли, реальный доступный срок; вопросы о налете, пяти сенсорах, ветре/радиусах/высотах/многовылетности отправлены | Ответов нет — записать допущения и разделить подтвержденные/пользовательские профили. Не приписывать допущения производителю |
| G1 — конец дня 3 | Простейшая сцена в метрах, валидный маршрут с настоящими маневрами, объяснимые ошибки | Нет базовой траектории 201 — подключить ограниченный параметризованный модельный режим, честно отметить пробел; заморозить CV/DEM/перепланирование и дизайн |
| G2 — конец дня 6 | Один полный расчет для нескольких БВС; обе цели; независимый валидатор; маленькая задача со сверенным ответом | Нет end-to-end — прекратить улучшение оптимизатора, оставить допустимый baseline + локальное улучшение; убрать P1. Не убирать обязательный экспорт/документацию |
| G3 — конец дня 9 | Резервная посадка/экспорт/совместимость проверены; все пять типов имеют честный статус; запуск на чистой машине | Открыты критические нарушения — не добавлять функции. Непроверенные сенсоры/рельеф пометить unsupported или experimental; оценить риск неполного соответствия ТЗ |
| G4 — конец дня 10 | Измерения воспроизводимы, сравнение честное, все принятые результаты валидны | Нет устойчивого выигрыша — показывать фактическую паритетность/различия и ограничения; не подбирать только выигрышные сцены и не рисовать проценты |
| G5 — день 12 | Чистый запуск, проверенные файлы, резервная демонстрация, обязательные материалы | Критический дефект — вернуть последний проверенный комплект. Предзаписанное видео не выдавать за успешный живой расчет |

Пример критериев приемки, предлагаемых командой, а не организатором: ноль нарушений hard constraints в принятом наборе; сравнение с baseline на одинаковых входах; ограничение времени расчета и его явный статус; экспорт всех обязательных полей; повторяемость при фиксированном seed. Числовой SLA по размерам и времени утвердить после первого измерения. «Всегда на 30% быстрее» заранее не обещать.

## 6. Если осталось 48–72 часа

При принятой загрузке 6 часов в день на человека это **24–36 человеко-часов за 2–3 дня**, а не 96–144. За такой срок нельзя честно обещать ту же полноту, что за 12 рабочих дней.

Аварийный результат — **ограниченный конкурсный прототип с открытой матрицей соответствия**, а не «полностью выполненное ТЗ»:

- Один небольшой плоский район, постоянный заданный ветер, один вылет на аппарат; ограничения явно показаны до расчета.
- Удержать карту, все поля входа, несколько аппаратов, две цели, объяснимое распределение, проверку зон и бюджета, состав индивидуального задания, KML/GeoJSON, README и известные ограничения.
- Работать только с профилями, для которых успели проверить положительный расчет. Остальные не удалять из реестра требований: отмечать «не реализовано/не подтверждено». Если 201 не проходит маневры, не заменять самолет коптерной змейкой.

## 8. Минимальный комплект доказательств на защиту

1. Матрица всех пунктов ТЗ: выполнено / частично / не проверено; ссылка на сценарий или файл, а не только слайд.
2. Два расчета одного входа с двумя целями; маленький объяснимый пример различий. Цели могут совпасть на отдельных сценах — это нормально, результат не надо искусственно менять.
3. Один составной позитивный сценарий и минимум один объяснимый отказ по ограничениям; на экране видны все полетные этапы и статус валидатора.
4. Реальные измерения против baseline с равными ограничениями; время расчета, размер задачи, машина, версии, seed, валидность и покрытие. Никаких заранее назначенных процентов улучшения.
5. Индивидуальные KML/GeoJSON и round-trip; демонстрация обязательных полей, а не только открытия линии на карте.
6. Чистый запуск, исходники, исполняемая версия/демо, архитектура, алгоритм, API при наличии, руководство и ограничения — то, что прямо требует ТЗ.
7. Презентация по предоставленному шаблону: обязательные титул/задача/команда, суть/уникальность, развитие, роли и подтвержденные контакты участников, реальные сложности. Не подменять обязательные блоки исключительно техническими слайдами.

**Сильная позиция на вопрос эксперта:** «Вот вход, допущения, найденное расписание, независимые проверки, экспорт и повторяемая команда запуска. Вот что не поддержано. Вот подтвержденное сравнение». Это защищает проект лучше, чем обещание нейросетевого оптимума или полетной безопасности без данных.
